Adversarial whole-subsystem review. Diff-scoped reviewers structurally miss
cross-file invariants, workflow-ordering properties, and live-artefact behaviour;
this pass looks for exactly those. Read `AGENTS.md` first and follow its routing
table for the scope's context docs. Never edit code in this pass; findings become
issues, process improvements become a PR against this skill.

## Procedure

1. **Ledger.** Find the open issue labelled `finder-ledger` whose title is
   `finder ledger: <scope>` (create it if absent, one per scope). Read its
   latest comment: head SHA last reviewed, findings then, open dead ends,
   process notes. If none, this is round 1.
2. **Delta.** `git log --oneline <last-sha>..HEAD -- <roots>` and the closed/opened
   issues touching the scope since that date. New code since last review gets the
   deepest read; ground reviewed clean and untouched since is skimmed, not
   re-derived. Re-check every previous finding that was open.
3. **Invariants first.** From the scope's docs write the 5–10 invariants the
   subsystem promises (ordering, idempotency, single source of truth, fail-closed,
   parity across siblings — v4/v6, CE/Plus, channels, languages). For each, find
   where the code enforces it and try to break it with an EXECUTED probe (`uv run
   pytest`, `vendor/bin/phpunit` or `shellspec --shell dash` for suites, after
   `uv sync --locked --group dev` / `composer install`; scratch dirs under `/tmp`;
   never the live boxes from the cloud). Also run `/code-review` at `medium`
   effort over the roots when the delta is large — its findings enter the same dedupe below. That
   command is a Claude Code client built-in, not a repo skill under
   `.agents/skills/`; a client without it skips this step and relies on the
   invariant probes above.
4. **Dedupe + cluster.** Before filing: `gh issue list --search` on the symptom
   words and the file names, open AND closed. One root cause = ONE issue with
   sub-items; siblings of the same rule are sub-items, never separate tickets.
   Hard cap: 5 new issues per run; overflow goes into the ledger comment as
   "unfiled leads" for the next run.
5. **File.** `gh issue create --type Bug|Task` (labels only for orthogonal
   routing: `CI`, `dnsbl`, `security`). Body: summary; executed evidence
   (commands + output tails, run URLs); root cause with file+symbol refs (never
   `file:NNN` line anchors); expected behaviour; RED-first test table (test name →
   what it pins → why it fails today); out-of-scope list; the `issues.md`
   scanner gate block when the finding is a hardening/scanner-class claim.
   Footer: `🤖 Generated by [Claude Code](https://claude.com/claude-code), posted
   via @<gh-login>'s account on their behalf.`
6. **Ledger comment** (always, even with zero findings): head SHA reviewed;
   invariants checked (✓/✗ + probe); issues filed; unfiled leads; dead ends and
   zero-yield commands (name them — the next run skips them); wall-clock per
   phase.
7. **Introspect + improve.** Compare this run's dead ends with the ledger's
   earlier ones. If a step, probe, or scope row is repeatedly useless or a
   better probe was found, edit THIS skill and open a PR against `devel`
   (dev-only class; title `skills: subsystem-sweep — <change>`; body cites the
   ledger comments that motivate it). Never push to `devel` directly from the
   routine.

## Rules

- No fabricated evidence: every filed claim has an executed command behind it.
- Ticket quality over count; a finding without a repro is an "unfiled lead".
- Do not comment on #2411 or on other issues except to link a duplicate.
- If `gh` is unauthenticated in the environment, do everything except step 5–7
  and print the would-be issues + ledger comment as the final message.
