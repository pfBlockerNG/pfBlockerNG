ACTION PLAN (ordered)

1. Add the pure scanner to pfblockerng.inc (end of the pure-helper block):

       function pfb_text_sanity(string $sample): ?string

   Returns NULL if the sample looks like plausible blocklist text, else a short
   reason token. PURE: string in, ?string out, no I/O, no globals. BYTE-LEVEL
   matching only — NO `/u` modifier anywhere (every pattern below is ASCII; byte
   matching cannot be flipped by a chunk-truncated multibyte tail — §2.1).

   Evaluate in THIS order, first hit wins:

   a) 'nul_bytes' — if the sample contains ANY NUL byte
      (strpos($sample, "\x00") !== FALSE). NUL in a text feed is unambiguous.

   b) 'html_error_page' — if the sample, left-trimmed of leading whitespace,
      begins (case-insensitive) with "<!doctype html" OR "<html", AND NONE of the
      first 20 lines is a "blocklist-shaped" line. Blocklist-shaped = any ONE of:
        - an IPv4/IPv6 address or CIDR;
        - a hosts-style line: an IP, whitespace, then a domain token;
        - a bare or ABP-wrapped domain.tld token (e.g. `example.org`,
          `||example.org^`).
      (This is the false-positive guard: an HTML-ish feed that DOES carry
      blocklist lines is NOT flagged.)

   c) 'below_min_content' — floor = 1: if the sample has ZERO non-blank,
      non-comment lines. A comment line begins with '#' or '!' after trimming
      leading whitespace. A legitimate single data line passes.
      This is a LINE-count floor, NEVER a byte-size floor: a short feed (well
      under 8 KiB, even a few bytes) is a COMPLETE sample, not a truncated one —
      do NOT add any "sample too small / too short" heuristic. The 8 KiB is only
      the read cap Phase 2 applies; the scanner receives whatever bytes exist.

   d) otherwise NULL.

   Doc-comment states the three tokens, the verdict order, and the byte-level /
   default-off contract (professional grammar). The scanner does NOT know the
   MIME or the flag — Phase 2 owns the gating (MIME scope + pfb_feed_sanity).

BRANCH COVERAGE — every verdict AND its guard, each an intent-named test:
- Real blocklist samples -> NULL: a plain IPv4/CIDR list; a hosts-style
  `0.0.0.0 domain` list; an ABP `||domain^` list; a single legitimate data line
  (proves floor=1 passes one line); a TINY feed of just a few bytes (e.g.
  "1.2.3.4\n") -> NULL (proves a short body is complete, NOT size-penalised); a
  comment-header-then-data body (`# license\n# ...\n0.0.0.0 x.example`) -> NULL
  (comments don't count against the floor but the data line satisfies it).
- 'nul_bytes': a sample with an embedded "\x00" -> 'nul_bytes', INCLUDING a
  sample that is otherwise valid blocklist text (proves NUL wins first).
- 'html_error_page': "<!doctype html>...</html>" with no blocklist token -> the
  token; "<html>" lower/upper/mixed case + leading whitespace/newlines -> still
  fires (case + leading-whitespace tolerance). GUARD: an HTML body that ALSO
  contains a blocklist-shaped line in the first 20 -> NULL (not flagged).
- 'below_min_content': empty string -> 'below_min_content'; whitespace-only ->
  same; comment-only body (`# a\n! b\n`) -> same (zero non-comment lines).
- Order proof: a NUL-bearing HTML error page -> 'nul_bytes' (a->b), and an
  all-comment HTML-less body -> 'below_min_content'.
- Truncation: an 8 KiB sample whose final line is cut mid-token, and a sample
  whose last bytes are a split multibyte UTF-8 char -> the multibyte tail does
  NOT change the verdict (byte-level; construct one valid-blocklist case that
  stays NULL with a dangling partial multibyte byte appended).
