Round-trip contract
-------------------
Select name: ``action-{r_id}``  (e.g. ``action-0``, ``action-1``).
Posted values: ``'Deny'`` | ``'Permit'``.

Saved by the **existing generic rowhelper loop** at
``pfblockerng_category_edit.php:~820``:

    config_set_path(
        "installedpackages/{$conf_type}/config/{$rowid}/row/{$k_field[1]}/{$k_field[0]}",
        $value
    );

For ``action-0``: ``$k_field[0] = 'action'``, ``$k_field[1] = '0'`` →
saves to ``installedpackages/pfblockerngdnsbl/config/{rowid}/row/0/action``.

This is the exact path Phase 4 reads (``$row['action'] ?? ''``).  No new save
path was needed — the generic rowhelper already handles it, exactly as it handles
``state-N``, ``format-N``, ``header-N``, and ``logging-N`` (note: ``logging`` here
refers to the group-level field, not per-row; per-row only has ``state``/``url``/
``header``/``format``/``action``).

Dynamic per-row key (parallel to ``logging``, ``custom``) — NOT routed through
PfbConfig (foreign-key exclusion, same as
``pfblockerngdnsbl/config/{group}/row/{idx}/custom``).  The dynamic path uses
variable interpolation so the ``RequireConfigGateway`` sniff is unaffected.

Values pass through ``pfb_filter($value, PFB_FILTER_HTML, ...)`` in the rowhelper
save — ``'Permit'`` and ``'Deny'`` carry no HTML special characters and survive
unchanged.

The absent ↔ 'Deny' round-trip is transparent: a pre-Phase-5 row with no stored
``action`` key displays as Deny (the guard ``=== 'Permit'`` treats absent as Deny)
and saves back as ``'Deny'`` on next form submission — no data loss, no forced
migration.

Note for Phase 6 (smoke journey)
---------------------------------
To mark a DNSBL feed row as Permit for the smoke journey:

1. In the test's config setup, set the per-row ``action`` key directly in
   ``config.xml`` (via the harness's config helpers):

       installedpackages/pfblockerngdnsbl/config/{group_idx}/row/{row_idx}/action = 'Permit'

2. Alternatively, use the UI: navigate to DNSBL → (group) → edit the alias →
   Source Definitions table → change the ``Action`` dropdown for the desired
   row from ``Deny`` to ``Permit`` → Save.

3. After saving, trigger a "Force Reload - DNSBL" so ``sync_package_pfblockerng()``
   regenerates the manifest with ``"mode": "permit"`` for that feed.

4. Verify: the domains from the Permit feed resolve normally (not blocked) despite
   being listed — confirming the band-2 allow overrides any block feed.

The exact config path for the smoke harness:
  - Group index: whichever group holds the test feed (0-based)
  - Row index: whichever row within that group's ``row`` array holds the Permit feed
  - Key: ``action``, value: ``'Permit'``
