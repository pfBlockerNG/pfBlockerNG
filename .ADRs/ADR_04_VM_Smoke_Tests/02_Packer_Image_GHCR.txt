ROLE

The build is SPLIT into two layers with one output contract: (a) the BASE OS install

WHY THIS PHASE EXISTS
Phase 1 proved a GH-hosted runner can boot+drive a hand-built pfSense VM. This phase
makes the image reproducible + refreshable on a CE bump and publishes it to GHCR so
the test workflow (Phase 6) just pulls it. Fully unattended pfSense CE install is
unofficial, fragile, and version-sensitive (installerconfig/rc.local media surgery, or
boot_command keystrokes) — so it is NOT a prerequisite. The seam is the published
qcow2: everything downstream consumes only `oras pull`, so the base OS can be installed
by hand once per CE version while the bakeable provisioning stays scripted and
reproducible. CE ONLY — pfSense Plus is a licensing nightmare, out of scope. The image
is PRIVATE in GHCR (Netgate trademark/binary redistribution — see §3).

ACTION PLAN (ordered)
1. BASE OS — CANONICAL mode is "seed once, upgrade in place":
   - SEED (manual, once): a documented runbook for the maintainer to do ONE clean
     manual pfSense CE install -> archive it as the immutable seed qcow2. This is the
     reproducibility anchor; never overwrite it.
   - VERSION BUMP (scripted, default path): boot the prior published image, run the
     pfSense upgrader over SSH (`pfSense-upgrade` — the CLI behind System > Update;
     confirm the exact non-interactive flags during the spike, don't guess), wait on a
     readiness signal (upgrade done + reboot + services up, NOT a fixed sleep),
     re-snapshot. RE-BASELINE with a fresh manual seed on a MAJOR version jump (the
     upgrader is riskiest there and cruft matters); upgrade-in-place for patch/minor.
   - OPTIONAL (spike-gated, NOT required): automate the clean install with Packer
     from ISO (installerconfig/rc.local surgery or boot_command keystrokes). Time-box
     it; if fragile, the manual seed already covers it — MOVE ON, do not rabbit-hole.
   - In all cases the Packer QEMU builder consumes the base via `disk_image = true`
     (boot existing qcow2, no ISO) and runs only the provisioning in step 2.
2. PROVISIONERS (always automated, run on whichever base) — bake in, idempotently:
   - a TEST SSH public key + root SSH enabled (the key the harness uses);
   - pfBlockerNG-devel INSTALLED (so all deps/dirs exist; the harness then rsyncs the
     branch over it via deploy.sh);
   - a known base config.xml (interfaces, services up);
   - Unbound `local-data` for the hermetic control domain(s) named in 01_Results.txt;
   - serial console retained for CI boot logs.
3. OUTPUT: a qcow2. Keep it small (compact/zero free space) — it travels over GHCR.
4. BUILD WORKFLOW (`.github/workflows/build-image.yml`): triggers
   `workflow_dispatch` (inputs: target PFSENSE_CE_VERSION, and base-source = seed |
   prior-version-to-upgrade) + `schedule`. Steps: ensure /dev/kvm; install packer +
   qemu + oras; `oras pull` the chosen base (seed or prior snapshot); if upgrading, run
   the pfSense-upgrade step (step 1) before provisioning; `packer build` (provisioning
   via disk_image=true); `oras push` the result to ghcr.io/<org>/<repo>/pfsense-ce
   tagged `:<PFSENSE_CE_VERSION>`. **RETAIN the seed and every version snapshot — never
   overwrite** (recoverability + audit; ADR §2 versioning). Use GITHUB_TOKEN with
   packages:write; the package is PRIVATE.
5. PROVE IT: after push, a verification step (or reuse the Phase 1 spike workflow)
   pulls the freshly published image and runs the Phase 1 round-trip — the
   reproducible image must boot + pass the same SSH/pfctl/dig/php-update checks.

CONSTRAINTS

- GHCR package PRIVATE. Do not publish the image publicly. Do not commit the SSH
