ROLE
You are on the `adr/04` branch (off `devel`) performing Phase 1 of ADR-04. This is
a DE-RISKING SPIKE, not the real harness: prove that a GitHub-hosted `ubuntu-latest`
runner can boot a real pfSense VM under KVM and that we can drive it (SSH + pfctl +
dig + the pfBlockerNG PHP CLI). Produce MEASURED numbers and a go/no-go against the
kill-threshold in §7 BEFORE any Packer work (Phase 2) is attempted. Work inline on
`adr/04`, one commit, push directly (no worktree isolation — project workflow).

WHY THIS PHASE EXISTS
ADR-01 was fully built (8 phases) and then REJECTED because its premise did not
hold. This ADR's premise — "a GH-hosted runner can cheaply boot+drive a pfSense CE
VM" — is unproven on TWO axes: (a) /dev/kvm is exposed and fast enough for a FreeBSD
guest; (b) the SSH/pfctl/dig/PHP-CLI round-trip works post-boot. If either fails the
budget, we pivot to self-hosted or a gated trigger — and we must learn that NOW, for
the price of one workflow, not after building the Packer template and the matrix.
This phase uses a HAND-BUILT pfSense+pfBlockerNG qcow2 (maintainer-provided, stored
privately); making that image reproducible is Phase 2's job, deliberately deferred.

ACTION PLAN (ordered — prove the cheapest thing first)
1. KVM PRESENCE: a workflow step that asserts `/dev/kvm` exists and is usable on
   `ubuntu-latest` (e.g. `kvm-ok` or `ls -l /dev/kvm` + a tiny qemu accel probe).
   If absent, that alone is a partial no-go — record it.
2. BOOT HELPER (POSIX sh, quoted, absolute paths): `tests/smoke/boot_vm.sh` (or
   similar) that launches `qemu-system-x86_64 -enable-kvm` headless, serial console,
   with QEMU user-net `hostfwd` mapping: tcp 2222->22 (SSH) and udp+tcp <p>->53 (DNS),
   and the host alias 10.0.2.2 reachable from the guest. Image path is a parameter.
3. READINESS WAIT (no fixed sleeps): poll until SSH answers on 2222 with bounded
   backoff + a hard timeout; capture boot-to-ready seconds.
4. CONTROL ROUND-TRIP over SSH (baked key): `pfctl -sr` returns rules; run
   `/usr/local/bin/php /usr/local/www/pfblockerng/pfblockerng.php update` and capture
   exit status; `dig +short @127.0.0.1 -p <p> <a-baked-local-data-name>` from the
   runner returns the expected answer. (The image must have a known local-data name
   baked in for a deterministic dig; the maintainer provides it with the image.)
5. STABILITY: run the boot+round-trip N>=5 times (matrix or loop); record pass count
   and boot-time distribution.
6. WORKFLOW: `.github/workflows/smoke-spike.yml` (workflow_dispatch) wiring 1-5 and
   printing the numbers. How the hand-built image reaches the runner (private GHCR via
   oras, or a temporary secret-guarded URL) is a spike convenience — document whatever
   you choose; Phase 2 replaces it with the reproducible GHCR image.
