ROLE
You are on the `adr/09` branch (off `devel`) performing Phase 1 of ADR-09. This is a
DE-RISKING SPIKE, not the release pipeline: prove that a GitHub-hosted FreeBSD VM can
build the pfSense-pkg-pfBlockerNG[-devel] port into an INSTALLABLE .pkg from this
repo's source, for the current CE's FreeBSD major. Produce MEASURED numbers and a
go/no-go against the kill-threshold (§7) BEFORE the release wiring (Phase 3). Work
inline on `adr/09`, one commit, push directly (no worktree isolation — project workflow).

WHY THIS PHASE EXISTS
ADR-01 was fully built and then REJECTED because its premise did not hold. ADR-09's
release-side premise — "a GH FreeBSD VM can build our port into an installable .pkg
cheaply" — is unproven IN CI. The maintainer already builds it manually via
`make package` (README "Building via the FreeBSD ports system"), so the risk is
reproducing that in a VM action within budget, with deps (net/libmaxminddb) resolving.
If it can't, the release artifact falls back to manual build+upload — learn that NOW,
for the price of one workflow, not after building the matrix + release wiring.

ACTION PLAN (ordered — prove the cheapest thing first)
1. FREEBSD VM: a workflow that runs a FreeBSD VM whose version MATCHES the current CE's
   FreeBSD major (e.g. FreeBSD 15 for CE 2.8). Use `vmactions/freebsd-vm` (pin the
   version) or a hand-rolled QEMU FreeBSD VM; document the choice + version.
2. PORTS TREE + SOURCE: inside the VM, make the port build from THIS repo's working tree
   (override GH_TAGNAME/WRKSRC, or stage src/ into WRKSRC) rather than fetching a tag, so

3. BUILD: `make package` (or `make stage && make package`) → confirm a .pkg in work/pkg/.

4. INSTALL CHECK: `pkg add` the produced .pkg on a clean pkg root inside the VM (or

5. WORKFLOW: `.github/workflows/build-spike.yml` (workflow_dispatch) wiring 1-4 and
   printing the numbers. Record them in RESULTS/01_Results.txt.
