ACTION PLAN (ordered)
1. STORAGE — `ci-metadata` orphan ref: store `supported-versions.json` on a `ci-metadata`
   ORPHAN branch (its own history, NOT in main->devel->next), the single source of truth.
   NOT a repo variable (variables have no git audit trail on a user repo — no
   diff/blame/rollback/PR review — and need a privileged token to write). Protect the
   branch (PR-only) and add a STATIC POINTER to it in scripts/README.md + CLAUDE.md so it
   is discoverable. Workflows read it at runtime (e.g. `git show
   origin/ci-metadata:supported-versions.json`, or actions/checkout of that ref with the
   default token). A future move to a dedicated public `pfBlockerNG-ci-infra` repo (read
   via raw URL, no token) is a mechanical swap — NOTE it, do not build it.
2. SCHEMA: each entry `{ pfsense_version, channel: CE|Plus, freebsd_version,
   freebsd_major, php_version, status: beta|GA, ci: bool }`. It carries the FULL
   (freebsd_version, php_version) BUILD PAIR (ADR §1 fact 2) — the build env needs the
   PHP pin, not just the major. Seed today's REAL support set ONLY:
   2.8.x -> { freebsd_version: "15.0-RELEASE", freebsd_major: "15", php_version: "8.3" }
   (CE, GA, ci:true); current Plus -> its FreeBSD major + PHP (Plus, GA, ci:false).
   DO NOT seed 2.7.x — it is below MIN_PFSENSE_VERSION (2.8.0) and unsupported. Keep the
   pairs identical to docs/misc/pfSense_versions.md and build-image.yml's resolve-version.
3. READER: a composite action or POSIX-sh helper that reads the matrix and emits, as
   workflow outputs: (a) the BUILD matrix = one entry per supported version, each
   carrying its `(freebsd_version, php_version)` pair (artifacts later DEDUP by distinct
   freebsd_major — ABI — but the build is driven by the pair); (b) the CI matrix = the
   `ci: true` CE entries. Pure read; no writes anywhere.
4. RECONCILE #22: repoint `build-image.yml`'s `resolve-version` job to DERIVE
   (freebsd_version, php_version) from THIS matrix (read the `ci-metadata` JSON) instead
   of its hardcoded `case`, keeping the same hard-fail-on-unknown behaviour — so a new
   version is added in ONE place (the matrix). Keep the reject-unknown contract intact.
5. LIFECYCLE DOC: document the policy next to the matrix — ADD on beta (curated), DROP
   the oldest CE only when the newest CE goes GA; Plus is always ci:false (build-only).
6. SELF-TEST: a tiny workflow (workflow_dispatch) that runs the reader and prints both
   emitted matrices (build pairs + CI entries), proving it parses the seed correctly.
