ACTION PLAN
1. Create `net/pfSense-pkg-pfblockerng-repo/` on `pfblockerng/use-github`: Makefile (PORTNAME
   `pfSense-pkg-pfblockerng-repo` or agreed name; arch-/version-independent content; NO_BUILD;
   GH_ACCOUNT=pfBlockerNG; SUB_FILES lists `pkg-post-install pkg-post-deinstall`), pkg-plist (the
   detection helper + any shipped conf-writer under share/), pkg-descr.
2. `pkg-post-install.in`: source the detection helper, compute `<channel>/<varver>/<arch>`, write
   the resolved conf to `/usr/local/etc/pkg/repos/pfblockerng.conf` (release) using the EXACT
   byte-identical template (priority 100, signature_type none, mirror_type none, enabled yes), then
   `pkg update`. Guard on `$2` phase (POST-INSTALL) per pfSense's pkg-install convention. Make it
   idempotent (re-running rewrites identical bytes).
3. `pkg-post-deinstall.in`: remove the conf it owns (only the pfblockerng.conf it wrote). Guard on
   the deinstall phase.
4. Decide channel handling: the meta-package defaults to the release conf; document how a nightly
   meta-package (or a flag) would write `pfblockerng-nightly.conf` — keep release-only unless the
   nightly channel needs its own meta-package (note the decision in the handoff).
5. Off-box test in this repo: build the `.pkg` via `build-pkg-portable.py` against the new port and
   assert the manifest's `scripts.post-install` / `scripts.post-deinstall` contain the SUB_LIST-
   substituted bodies, and that a simulated run writes a conf byte-identical to `--print-conf` for
   sample boxes (CE 2.8/amd64, Plus 26.03/aarch64).

CONSTRAINTS
- pkg-post-install/deinstall: POSIX sh, base system only — NO PHP, NO add-on deps (runs under
  libpkg). Quote expansions; LC_ALL=C on compares.
- Reuse the Phase-1 helper verbatim — do NOT reimplement detection.
- Conf bytes MUST match the generators' template (Phase 4 keeps all in lockstep).

VERIFICATION
