HOSTILE-INPUT ROWS (REQUIRED test data -- fill in the observed result for each; the guard from
step 3 must handle every one without dropping/duplicating/corrupting a row, and without
aborting the rest of the save):
- Posted order array missing an index that exists in the current row set (e.g. 3 rows, posted
  order names only 2 of them) -> reorder skipped, all 3 rows survive unchanged in original order.
- Posted order array with a duplicate index (e.g. [0, 1, 1]) -> reorder skipped, no row
  duplicated in $rowdata.
- Posted order array with a foreign/stale index (references a row key from a PRIOR page state,
  e.g. a row deleted in a concurrent tab) -> reorder skipped, current row set unchanged.
- Posted order field is a non-array (string, int, bool) -> reorder skipped, no TypeError, no
  crash (mirrors #1106/#1128/#1139-class array-valued-field guard discipline already
  established elsewhere in this file -- grep the existing pfb_filter/array guards for the
  house pattern before inventing a new one).
- Posted order field is empty/absent -> reorder skipped silently (no manual-reorder attempted,
  e.g. the request came from sort=='sort' mode or a non-reorder save) -- must NOT be treated as
  an error, just "nothing to reorder."
- A VALID posted order combined with a field edit (e.g. changing header-1's value) in the SAME
  request -> both apply correctly: the row is both reordered AND has its edited field reflected
  at its NEW position.
