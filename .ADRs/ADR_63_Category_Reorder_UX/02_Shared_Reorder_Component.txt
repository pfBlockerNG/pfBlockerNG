COMPONENT CONTRACT (§2 Decision 1 — implement exactly this surface)
- init takes: container selector, ROW selector ('tr.sortable' on one page,
  '.form-group.repeatable' on the other), an onAfterMove callback, and a boolean enabling drag
  (the roworderdragging read happens server-side in Phase 3/4 and arrives here as a plain
  parameter).
- Drag: thin generalisation of category.php's existing .sortable() options; init only when the
  drag boolean allows.
- Anchor-click: checkbox-per-row + per-row anchor button; click = move checked rows BEFORE the
  clicked row, shift-click = AFTER (firewall_rules.php UX, re-implemented on our markup).
  Anchor buttons are type="button" — NEVER type="submit" (the old category_edit anchor
  submitted the form per click; copying that markup is a regression).
- After EVERY completed move (drag stop or anchor-click), call onAfterMove.
- Order-read helper: returns the current DOM order of row ids in the exact ids[] wire format
  ("ids[]=rN&…"), computed from the DOM directly — it must work when .sortable() was NEVER
  initialised (ADR §1.8: sortable('serialize') throws in that case; this helper replaces it).
- Event handling is DELEGATED (bound on the container): core renumber() rewrites the name/id
  of every input/select/button inside repeatable groups, so per-element bindings go stale.
- Any control the component injects per row carries a trailing-digit-suffixed name/id (so
  renumber() rewrites it consistently on the repeatable page).
- The component NEVER reads or writes any other per-row named field, and NEVER
  disables/enables any Save button (both pages' Save buttons are general-purpose — ADR §1.8).
