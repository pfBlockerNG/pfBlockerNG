WHY THIS PHASE EXISTS
ADR-20's primary mechanism (dynamic routing: a Cloudflare Worker reads the
pkg-injected User-Agent to route CE vs Plus requests to the correct catalog subtree)
rests on one unverified premise: does the pfSense-injected `User-Agent` header
reach a server behind HTTPS and CDN layers, or is it stripped/replaced? GitHub Pages
is behind Fastly; a Cloudflare Worker sits in front. If the UA is absent or a
generic CDN string when the Worker sees it, the dynamic routing approach is REJECTED
before any Worker code is written. The ADR-01 guard: falsify the premise cheaply
before building on it.

The secondary premise — `globals.plus.inc` EXISTS on Plus and is ABSENT on CE — is
already confirmed by the live probe (2026-06-09) and needs only to be recorded as GO
in the handoff; no further verification is required.

ACTION PLAN (ordered)
1. DEPLOY a minimal HTTPS logging endpoint. The simplest option:
   - A Cloudflare Worker (free tier, no KV) at a `*.workers.dev` URL whose handler
     is: `return new Response(request.headers.get('User-Agent') ?? '(absent)')`.
     Deploy via `wrangler deploy` from a minimal `wrangler.toml` project (no account
     secrets needed for a free Worker returning the header). The response body IS
     the UA string; no log aggregation needed — the requester sees it in the body.
   - Alternatively: a `requestbin`-style service or any HTTPS endpoint that echoes
     the `User-Agent` header in the response body. The requirement is HTTPS (pkg
     refuses HTTP for repo fetches) and that the endpoint is NOT GitHub Pages /
     Fastly (we need to isolate the CDN variable).
   Record the endpoint URL in the handoff.

2. HIT the endpoint from BOTH a CE box and a Plus box using pkg's network stack
   (not curl — pkg is what sets the UA). Method: write a minimal `pkg.conf` pointing
   the `pfblockerng-test` repo to the endpoint URL and run `pkg update -r
   pfblockerng-test`. The endpoint returns the UA in the response body; pkg will error
   (not a valid repo), but the RESPONSE BODY (UA string) is visible in `pkg -d update`
   verbose output or by reading the raw HTTP response from the Worker logs /
   requestbin. Alternatively, wrap the Worker to return a valid but empty `meta.conf`
   so pkg doesn't error — whichever approach makes the UA value readable.
   If live CE/Plus boxes are not available for this test, document the constraint and
   use the `pkg -d` verbose output from a test repo fetch (the UA is sent on every
   pkg HTTPS request; check `pkg -vv` to confirm CURLOPT_USERAGENT is set from
   `PKG_ENV["HTTP_USER_AGENT"]`).

3. READ the UA value from the endpoint or verbose pkg output. Classify:
   - GO: the string reaching the endpoint matches the pfSense-injected format
     (`pfSense/...` or `Netgate pfSense Plus/...`), with the `Plus` token present
     on Plus and absent on CE. The CDN/HTTPS path did NOT replace it with a generic
     string (e.g. `Fastly/...`, `CF-Worker/...`, `pkg/1.21`, or `(absent)`).
   - REJECT: the UA is absent, replaced, or identical on both CE and Plus. Document
     the actual observed string and the network path.

4. RECORD the `globals.plus.inc` verdict: the live probe already confirmed
   EXISTS on Plus / ABSENT on CE. Mark as GO; no re-verification needed. Quote the
   probe output section (§6 "CE VS PLUS FILESYSTEM DISCRIMINATORS") in the handoff.
