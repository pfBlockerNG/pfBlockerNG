WHY THIS PHASE EXISTS
Phase 4 writes the Worker URL into the conf. Without the Worker, pkg fetches fail.
This phase deploys the Worker and makes the routing live. The key design decision:
the Worker is NOT hardcoded with version → catalog mappings. Instead it fetches
`routing.json` from Pages (edge-cached 5 min), matches the pfSense UA prefix against
route patterns, and 302-redirects to the version-keyed catalog dir. Adding or
retiring a pfSense version = edit `routing.json` only; no Worker redeploy needed.
This is the "conf written once, dynamic routing table" UX win.

ACTION PLAN (ONLY if Phase 1 USER_AGENT_VISIBLE = GO)

1. DESIGN the Worker logic (stateless, no KV; routing table from routing.json):
   ```javascript
   const ROUTING_MANIFEST_URL =
     'https://pfblockerng.github.io/pkg/routing.json';
   const CACHE_TTL = 300; // 5 minutes

   export default {
     async fetch(request, env, ctx) {
       const ua = request.headers.get('User-Agent') ?? '';
       const url = new URL(request.url);

       // Fetch routing.json, edge-cached for CACHE_TTL seconds.
       const routes = await getRoutes(ctx);
       if (!routes) {
         return new Response('Routing manifest unavailable', { status: 502 });
       }

       // Match UA against pattern prefixes (first match wins; most specific first).
       const route = routes.find(r => ua.includes(r.pattern));
       if (!route) {
         return new Response(
           `Unsupported pfSense version (UA: ${ua})`, { status: 404 });
       }

       // 302 redirect to version-keyed catalog dir.
       // Input path: /FreeBSD:15:amd64/packagesite.yaml.pkg
       // Output:     https://pfblockerng.github.io/pkg/ce-2.8/FreeBSD:15:amd64/...
       const target =
         `https://pfblockerng.github.io/pkg/${route.catalog}${url.pathname}`;
       return Response.redirect(target, 302);
     }
   };

   async function getRoutes(ctx) {
     const cache = caches.default;
     const cacheKey = new Request(ROUTING_MANIFEST_URL);
     let resp = await cache.match(cacheKey);
     if (!resp) {
       resp = await fetch(ROUTING_MANIFEST_URL);
       if (!resp.ok) return null;
       const ttlResp = new Response(resp.body, resp);
       ttlResp.headers.set('Cache-Control', `s-maxage=${CACHE_TTL}`);
       ctx.waitUntil(cache.put(cacheKey, ttlResp));
     }
     const data = await resp.clone().json();
     return data.routes ?? null;
   }
   ```
   Key design points:
   - routing.json patterns are matched as a substring (UA includes pattern).
     Patterns must be distinct enough to avoid false matches; the current set is safe
     (`pfSense/2.8` won't match a Plus UA).
   - First match wins; list more-specific patterns before less-specific ones in
     routing.json (e.g. `pfSense/2.9` before a hypothetical `pfSense/2` catch-all).
   - Only `active` vs `legacy` status distinction is in routing.json — the Worker
     treats both the same (routes to the catalog dir). Status is for the publish
     pipeline to know what to build; the Worker doesn't filter by it.
   - Worker failure modes: routing.json fetch fail → 502; no matching route → 404;
     never a silent wrong install.
