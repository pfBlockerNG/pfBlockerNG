WHY THIS PHASE EXISTS
With only static URLs from Phase 4, a CE conf on a Plus box fails dep-check (safe,
but requires a manual re-run of `add-repo.sh`). The routing layer eliminates that
manual step: a stale CE conf on a Plus box fetches the routing URL → the Worker
reads `User-Agent` → sees "Plus" → proxies/redirects to the Plus catalog →
dep-correct package returned. The CE→Plus migration becomes transparent at the
pkg-fetch level. The Worker is also the canonical URL clients should configure
going forward (a single URL that never changes even when the catalog layout evolves).

ACTION PLAN (ONLY if Phase 1 USER_AGENT_VISIBLE = GO)
1. DESIGN the Worker logic (stateless, no KV):
   ```javascript
   export default {
     async fetch(request) {
       const ua = request.headers.get('User-Agent') ?? '';
       const variant = ua.includes('Plus') ? 'plus' : 'ce';
       // Rewrite the URL: insert variant/ before the ABI segment
       // Input: https://pkg.pfblockerng.io/FreeBSD:16:amd64/...
       // Output: https://pfblockerng.github.io/pkg/plus/FreeBSD:16:amd64/...
       const url = new URL(request.url);
       const newUrl = `https://pfblockerng.github.io/pkg/${variant}${url.pathname}`;
       return fetch(newUrl, { headers: request.headers });
     }
   };
   ```
   The input URL structure is the routing URL with the `${ABI}` prefix already
   expanded client-side (pkg expands `${ABI}` before making the HTTPS request).
   The Worker rewrites `/<ABI>/...` → `/ce/<ABI>/...` or `/plus/<ABI>/...`.

2. VERIFY the URL rewrite logic handles ALL pkg fetch paths:
   - `meta.conf` → `https://pfblockerng.github.io/pkg/ce/FreeBSD:15:amd64/meta.conf`
   - `packagesite.yaml.pkg` → same path under the variant subdir
   - Individual `.pkg` files → same
   The `${ABI}` segment is always the first path component after the root (pkg's
   `url:` in the conf is `https://pkg.pfblockerng.io/${ABI}` — the Worker sees the
   ABI in `url.pathname`).
