DEVIATIONS / JUDGMENT CALLS
--------------------------------------------------------------------------------
1. IMPLEMENTATION CHOICE the brief left unspecified, resolved by executed probe:
   the brief's action plan says "prefix $log with {$now}" but does not specify
   HOW to handle a message with LEADING NEWLINES (e.g. the real "Download FAIL"
   call site is "\n\n [ ... ] Download FAIL [ NOW ]\n"). Two candidates were
   probed:
     (a) `"{$now} " . ltrim($log, "\n")` -- strips leading newlines entirely.
         Reproduces the brief's EXACT claimed header[4] regression numbers
         ('ProviderX' wrong / 'SomeFeed' after the fix) -- confirmed via
         executed php -r probe. BUT: breaks a load-bearing, DOCUMENTED
         convention (ADR-48's pfb_validate_log_line(): "Shape: leading \n per
         pfb_logger() convention" -- a PURE SEPARATOR from the PREVIOUS write,
         relied on by every pfb_validate_log() caller, since each message has
         NO trailing newline). Under ltrim, two consecutive same-call-site
         writes concatenate onto ONE physical line with no separator --
         confirmed via the full suite: PfbEmitEntryRejectStatsTest,
         LiveLogStdoutTest, PfbValidateLogTest all broke, one (
         testNonzeroBucketsEmitOneCanonicalLineEach) with a literal
         line-concatenation failure, not just a format mismatch.
     (b) `substr($log,0,$lead) . "{$now} " . substr($log,$lead)` where
         `$lead = strspn($log, "\n")` -- preserves ALL leading newlines
         verbatim (so the separator convention still works) and inserts the
         stamp right after them, before the actual content. Produces the
         IDENTICAL final content-line bytes as (a) for the header[4]
         regression's purposes (verified: same double-space artifact, same
         header[4] shift, same fix), while ALSO fixing the concatenation
         bug ADR-48's callers depend on.
   SHIPPED: (b). Confirmed via the full suite (2449/2449 green) that this
   choice does not regress any of the 8 downstream tests (a) broke.

2. COVERAGE-MATRIX GAP the brief's (and Phase 1's carry-forward's) own
   enumeration missed: `testLogWithNowTokenSubstitutesIsoTimestampWhenPnowCleared`
   was NOT in either's "6 tests to flip" list, but running the suite against
   the new pfb_logger() showed it ALSO fails (7 failures, not 6) --
   re-enumerated from the actual test run per CLAUDE.md's coverage-matrix
   discipline ("re-enumerate the class from the source, never from the
   finding's wording"), not silently left broken. Flipped to
   testLogLegacyNowTokenScrubbedNotSubstituted (item 5's list above already
   reflects the corrected 7).

3. UNENUMERATED DOWNSTREAM CONSUMERS: neither the brief nor ADR.md's coverage
   matrix names pfb_validate_log_line()'s callers (ADR-48/#789:
   PfbValidateLogTest, PfbEmitEntryRejectStatsTest) or LiveLogStdoutTest
   (ADR-58) as consumers of pfb_logger()'s exact output shape. Found by
   running the FULL `vendor/bin/phpunit` suite (not just the ADR's named
   test files) after the pfb_logger() rewrite -- 8 failures surfaced (3
   PfbValidateLogTest, 3 PfbEmitEntryRejectStatsTest, 2 LiveLogStdoutTest).
   All 8 were literal exact-match assertions against the PRE-stamp output;
   updated to match the new stamped shape (regex-based, still capable of
   failing on a real regression -- verified the zero-count-bucket
   "must NOT emit" assertion in PfbEmitEntryRejectStatsTest specifically,
   since a naive fix could have made it vacuously always-pass; rewrote it
   with assertDoesNotMatchRegularExpression against the STAMPED pattern so
   it still catches a wrongly-emitted line). None of these files are in
   ADR.md's Phase 2 scope by name, but they ARE pfb_logger() callers whose
   tests pin its exact byte output -- fixing them is required by "every
   change ships with green tests," not a scope expansion of the ADR itself.

4. Case 5 (debugger) simplification: dropped the redundant "{$now} | " prefix
   in `@file_put_contents("/tmp/pfb_debug", "{$elog}", FILE_APPEND);` since
   $elog now always carries its own leading stamp -- otherwise this internal,
   untested, out-of-scope debug path would silently double-print the
   timestamp. Judged a same-function correctness fix, not caller-string
   scope creep (case 5 is internal switch-case logic inside pfb_logger()
   itself, not one of the ~30+ caller message strings the constraints
   protect).

None of the above weakens any CLAUDE.md MUST rule. All are either (a) an
executed-probe-confirmed implementation choice where the brief was silent,
(b) a coverage gap closed per the mandatory re-enumeration rule, or (c) a
same-function robustness fix inside pfb_logger()/pfb_open_sqlite() -- no
caller message string, no ip_block/permit/matchlog/dnsbl_parse_err/dnslog/
dnsreplylog/unilog site was touched (verified via diff-read).

CARRY-FORWARD FOR PHASE 3 (pfb_daemon_filterlog()/pfb_parsed_fail())
--------------------------------------------------------------------------------
- Phase 3 touches the SAME file (pfblockerng.inc). pfb_logger()'s NEW shape is:
  `substr($log,0,strspn($log,"\n")) . "{$now} " . substr($log,strspn($log,"\n"))`
  -- i.e. the stamp lands right after any leading newlines in the message, not
  necessarily at absolute byte 0. If Phase 3's pfb_daemon_filterlog()/
  pfb_parsed_fail() rewrite calls pfb_logger() (rather than writing ip_block/
  permit/matchlog directly, which it does today via a separate path), re-verify
  this insertion point doesn't collide with whatever format Phase 3 introduces.
- pfb_failures()'s fix strips EXACTLY `^\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2} ` --
  if Phase 3 or later phases change pfb_log_iso_timestamp()'s format, this
  regex must move in lockstep (same coupling ADR.md §2.3 item 5 already flags).
- $pfb['pnow'] no longer exists ANYWHERE (grep confirms) -- Phase 3 must not
  reintroduce or reference it.
- Any NEW pfb_logger() caller Phase 3 adds should be checked against BOTH
  conventions now in play: "no leading newline" (most callers, gets a clean
  "{$now} text" line) and "leading \n as pure separator" (ADR-48's
  pfb_validate_log_line() family) -- pfb_logger() now handles both correctly,
  but a new caller mixing conventions (e.g. embedding an INTERIOR \n mid-
  message with no trailing \n) was not a coverage-matrix row here and is
  worth a fresh probe if Phase 3 introduces one.
- Full `vendor/bin/phpunit` (not just ADR.md's named test files) should be
  re-run after ANY pfb_logger()-shape change -- this phase's own gate caught
  3 unenumerated consumer files (DEVIATIONS #3) that ADR.md's coverage matrix
  never named; Phase 3 risks the same class of miss if it only checks the
  named rows.
