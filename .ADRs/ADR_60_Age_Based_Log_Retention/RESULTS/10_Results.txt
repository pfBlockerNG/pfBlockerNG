DECISION: pfb_iso_timestamp() -- KEPT, not simplified/removed
--------------------------------------------------------------------------------
Verified the planner's strong-lean-keep reasoning and agree: pfb_iso_timestamp()
has real, independent value beyond dnsbl_alias_update()'s no-year format --
it's issue #333's general "reformat any parseable date, else passthrough"
helper, already proven by its own 6 pre-existing tests (PfbIsoTimestampTest.php)
covering 3 branches (US-style-with-year, already-ISO round-trip, unparseable
passthrough) that this phase did not need to touch.

Concretely, once dnsbl_alias_update() writes real ISO-with-year values, a
FRESH value round-trips through pfb_iso_timestamp() as a no-op (proven by
DnsblAliasUpdateTimestampFormatTest::testUpdateModeStoresYearBearingIsoTimestamp,
which asserts `pfb_iso_timestamp($stamp) === $stamp` for a freshly-stored
value). But EXISTING installs upgrading to this fix have old no-year values
sitting in their live SQLite `dnsbl` table right now, for every DNSBL group
that hasn't had a dnsbl_alias_update('update', ...) call since the upgrade
(a disabled/inactive feed group could sit stale for a long time). Removing
pfb_iso_timestamp() would make those old rows display raw ('Jul  8 14:30:45',
unparsed by anything) instead of at least a best-effort guessed year. Keeping
it costs nothing (it's already a no-op on fresh values) and closes that
upgrade-window gap. DnsblAliasUpdateTimestampFormatTest::
testOldNoYearFormatLosesTheRealWriteYearOnReadback documents the residual risk
it still guards against (an old no-year value's real write year is
unrecoverable -- pfb_iso_timestamp() can only guess the CURRENT year, never
the true one -- but that's strictly better than showing the raw ambiguous
string with literally nothing reformatted).

DEVIATIONS / JUDGMENT CALLS
--------------------------------------------------------------------------------
1. dnsbl_alias_update()/pfBlockerNG_clearsqlite() write the ISO format via the
   plain `date('Y-m-d H:i:s', time())` literal (the same convention already
   dominant elsewhere in this file for non-managed-log timestamps, e.g.
   pfblockerng.inc:710 inside pfb_iso_timestamp() itself and :7162's
   py_unbound.ini "File created" comment), NOT via pfb_log_iso_timestamp().
   pfb_log_iso_timestamp()'s own comment scopes it explicitly to "pfBlockerNG's
   log writers" (its 5 existing call sites are all managed-log-file writers);
   dnsbl_alias_update()/pfBlockerNG_clearsqlite() write SQLite stat columns,
   not log files, so reusing the log-writer helper would misrepresent what
   these two functions are. This is a judgment call the brief explicitly left
   open ("your call, but stay consistent with whichever pattern is already
   dominant nearby") -- confirmed via grep that the bare literal IS the
   dominant non-log-writer convention in this file.
2. Added a `is_process_running()` PHPUnit double (tests/php/pfsense_doubles.php)
   -- required to call pfBlockerNG_clearsqlite('cleardnsbl') for real in a
   test (it reaches that function at runtime and no double existed). Strictly
   additive, function_exists()-guarded, matches the file's own documented
   convention; confirmed via a full phpunit re-run that no other test's
   behaviour changed (same pass/skip/deprecation counts as before, +16 new
   tests only).
3. Wrote 2 new Tier-A ui_render tests (Update page + widget) covering the
   format change specifically (not just relying on the existing generic
   test_page_renders_clean sweep, which only proves "still renders, no PHP
   error" -- not that the NEW format actually appears). Per the brief's own
   explicit ask ("Tier-A ui_render for any page whose displayed date format
   changed (the dashboard widget, the Update page)").
None of the above weakens any CLAUDE.md MUST rule.
