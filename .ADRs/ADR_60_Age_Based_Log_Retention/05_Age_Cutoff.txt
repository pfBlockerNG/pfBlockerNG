WHY THIS PHASE EXISTS
All 10 log types now share one uniform, always-present, year-bearing `Y-m-d H:i:s` timestamp
(Phases 2-4). This phase adds the actual age-based retention cap the user asked for: "if retention is
N days, trim lines older than N days from the file," implemented as one extra pass over
`pfb_log_mgmt()`'s existing line-count trim candidate.

ACTION PLAN
1. Register `log_max_days_<type>` in `pfb_cfg_registry()` — one entry per each of the 10 log types
   (`log, errlog, extraslog, ip_blocklog, ip_permitlog, ip_matchlog, dnslog, dnsbl_parse_err,
   dnsreplylog, unilog`), default `'0'` (numeric string, `'0'` = off), plain-string identity adapter
   (`NULL`/`NULL`), `'since' => '4.0.0'` — mirror the `log_max_<type>` loop's exact shape. Add all 10
   full paths (`installedpackages/pfblockerng/config/0/log_max_days_<type>`) to the sniff's
   `$registeredPaths`.
2. Restructure `pfb_log_mgmt()` so the `nolimit` early-`continue` (currently gates the WHOLE function
   body per type) only skips the LINE-COUNT step, not the age-cutoff step. Read `log_max_days_<type>`
   via `PfbConfig::read()`; treat a non-numeric/garbage value as `'0'` (off) — mirror
   `pfb_log_max_lines()`'s existing fallback-to-default pattern (adapt it, don't invent a new one).
3. Add the age-cutoff pass: it operates on the SAME candidate the line-count trim already produces
   (the `tail -n $logmax` output, or — when `log_max_<type> == 'nolimit'` — the whole file, since
   there's no line-count candidate to reuse in that case; decide and document which you read in that
   branch). Parse each candidate line's leading (free-text logs) or field-0/1 (CSV logs — reuse
   whichever field position Phases 2-4 established per type) `Y-m-d H:i:s` timestamp; scan from the
   top; drop the leading run older than `now - log_max_days_<type>` days; keep everything from the
   first non-expired line onward. A line with NO parseable timestamp (legacy pre-rework line) counts
   as expired (§2.2 "Unparseable line policy"). Write the result back through the SAME inode-preserving
   `cat`-over mechanism already in place (reuse it, don't duplicate the chroot/`chown unbound` handling
   — factor it into a shared helper if that's the cleanest fit, your call, but do not fork two copies
   of the chroot-path logic).
4. Gate every exec (`tail`/`cat`/your new scan) on its exit code exactly like the existing code does —
   a failed step must never blank or corrupt the live log (§2.3 item 6).
