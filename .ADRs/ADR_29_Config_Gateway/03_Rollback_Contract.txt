ROLE
You implement Phase 3 of ADR-29 on branch `adr/29-config-gateway`. BEHAVIOUR-PRESERVING
(tests + doc + an existing-smoke extension). This phase encodes the rollback contract and the
FALSIFIABLE gate every later migration phase relies on. Work inline, one commit, push directly.

WHY THIS PHASE EXISTS
ADR-28 froze the format FORWARD (new code reads old store). The #281 follow-up asks for SMOOTH
ROLLBACK too: old code reading what new code wrote. Because the gateway always writes the legacy
stored vocabulary, downgrades are safe by construction — but that guarantee is only real if a test
falsifies it. This phase builds that test.

ACTION PLAN
1. Encode each registry field's `since-version` (Phase 1 left the field; populate it from the key's
   introduction — current shipped version for legacy keys is acceptable as a baseline; document the
   convention). Add the invariant helper(s) the tests use.
2. Off-box rollback unit tests (tests/php/): for every registered field, assert the FORWARD invariant
   (read of any legacy stored value yields a sane runtime value) AND the BACKWARD invariant (write of
   any runtime value yields ONLY a legacy stored token an older release recognises — i.e. the write
   never emits a novel on-disk token). A field that cannot satisfy backward-safety is EXCLUDED and
   listed (mirror ADR-28's pfb_idn exclusion style).
3. Extend tests/smoke/test_upgrade_config_stability.py (or add a sibling `test_*_rollback`) with a
   DOWNGRADE leg: install the HIGHER build, write a representative settings spread through the
   package, snapshot config.xml, `pkg` downgrade/reinstall the LOWER build, then assert (a) the store
   is byte-identical and (b) the lower build reads sane values (a representative runtime behaviour —
   a blocked DNSBL name — still works). Reuse the existing forged-pkg + repo_vm machinery; keep the
   `repo` marker; never set pfb_keep (the #281 condition) — rely on the seed.
4. Document the rollback contract + any excluded field in CLAUDE.md (extend the Phase-1 policy text).
