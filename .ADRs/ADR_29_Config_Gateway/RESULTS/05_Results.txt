ADR-29 Phase 5 — Route install-time config access through the gateway
=====================================================================
Status: COMPLETE — all verification gates green
Date:   2026-06-19

## What was done

Routed all `installedpackages/pfblockerng*` reads and writes in
`pfblockerng_install.inc` through the `PfbConfig` gateway (`readSection`,
`writeSection`, `deleteSection`, `read`, `write`). Routed the migration
driver in `pfblockerng_extra.inc::pfb_run_migrations()` through the same API.
Foreign keys (non-`installedpackages/pfblockerng*` paths) left on direct
`config_*_path` calls, each annotated with the standard comment. Behaviour is
fully preserved — identical stored values, identical migration outcomes.

## pfblockerng_extra.inc changes

### pfb_run_migrations()

The migration driver now reads/writes via the gateway instead of calling
`config_get_path`/`config_set_path` directly:

  Before: $cfg = config_get_path($migration['section'], []);
          if ($result !== NULL) {
              config_set_path($migration['section'], $result);
          }

  After:  $cfg = PfbConfig::readSection($migration['section']);
          if ($result !== NULL) {
              PfbConfig::writeSection($migration['section'], $result);
          }

Behaviour unchanged — the migration closures receive and return the same
section array; write_config() is called on the same condition.

## Absent-section NULL semantics

`PfbConfig::readSection` returns `[]` (empty array) for an absent path, while
the original `config_get_path` returns `null`. Where downstream code calls
`is_array()` or `!= null` to distinguish absent from present sections, a
conversion is applied immediately after the readSection call:

  $x = PfbConfig::readSection(...);
  $x = empty($x) ? NULL : $x;

Affected sites: ET IQRisk, pfb_feed_internal_filter context read. All other
sites use `is_array()` or `!empty()` which treat both `[]` and `null` as
"absent" — no conversion needed there.
