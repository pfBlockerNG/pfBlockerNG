## Sniff: PfBlockerNG.Config.RequireConfigGateway

**File:** `tests/phpcs/PfBlockerNG/Sniffs/Config/RequireConfigGatewaySniff.php`

**Sniff code:** `PfBlockerNG.Config.RequireConfigGateway.RawRegisteredKeyAccess`

**Scope:** All `src/` PHP (`phpcs.xml.dist` scans `src/usr/local/pkg/pfblockerng` +
`src/usr/local/www`), with two `<exclude-pattern>` entries:
  - `pfblockerng_extra.inc` — the gateway implementation itself
  - `pfblockerng_migrate.inc` — migration driver shim

**What it flags:** A `config_get_path` / `config_set_path` / `config_del_path` call
whose first argument is a **static string literal** that exactly matches one of the
65 full paths in `$registeredPaths` (the `pfb_cfg_registry()` inventory embedded in
the sniff as a configurable property).

**What it does NOT flag (precision):**
  - Dynamic paths — first argument contains a variable or expression (T_VARIABLE,
    T_DOUBLE_QUOTED_STRING with interpolation, concatenation chains)
  - Non-registered foreign keys (pfblockerngipsettings/*, widget-*, per-row/per-feed
    dynamic keys, per-continent structures, pfSense-core sections)
  - Section-level reads (path ends at /config/0 or the section name; no trailing key)
  - The gateway file itself (pfblockerng_extra.inc — excluded via phpcs.xml.dist)
  - Out-of-scope keys per ADR-29 §2.5 (e.g. the raw `dnsbl_webpage` key used in
    pfblockerng_dnsbl.php is not in the registered path set; the registry has `dnsblwebpage`)

**Allow-list (foreign keys documented in source files, not flagged):**
See the complete foreign-key exclusion list now in CLAUDE.md "Config gateway — PfbConfig (ADR-29)"
section. All foreign annotations were committed in Phases 4–8.

## Stragglers routed to PfbConfig (4 sites)

The sniff found 4 genuine straggling registered-key raw accesses outside the gateway:

1. **`pfblockerng.inc` line 2272** — `config_get_path('...pfb_software_check', null)`
   in an anonymous function body (software update checker).
   → `PfbConfig::read('pfb_software_check')` (plain string; null default preserved
     since `PfbConfig::read` returns `''` for absent, and the caller handles both
     string and null via `is_string()` — `''` satisfies `is_string()` = TRUE, so
     behaviour is preserved; the caller was already null-hardened).

2. **`pfblockerng.inc` line 6273** — `config_get_path('...pfb_feed_internal_allowlist')`
   in `pfb_feed_internal_allowlist()`.
   → `PfbConfig::read('pfb_feed_internal_allowlist')` (plain string, default '').
     Caller: `!is_string($raw) || $raw === ''` — still correct; PfbConfig always
     returns a string (never null), so `is_string()` is always TRUE; empty default
     is identical to the old null-to-empty flow.

3. **`pfblockerng.inc` line 6438** — `config_get_path('...pfb_feed_internal_filter')`
   in `pfb_feed_filter_enabled()`.
   → `PfbConfig::read('pfb_feed_internal_filter')` (plain string, default 'on').
     Caller: `return ($value !== 'off')`. The registered default is `'on'`
     (absent = filter enabled), which matches the original raw-read behaviour
     (`config_get_path` returns null when absent; null !== 'off' = TRUE = enabled).
     Parity preserved.

4. **`pfblockerng_update.php` line 454** — `config_set_path('...pfb_reuse', 'on')`
   in the Force Reload handler.
   → `PfbConfig::write('pfb_reuse', 'on')` (plain string write; no adapter).
     Semantically identical — PfbConfig::write stores the exact string provided.

All four are behaviour-preserving; parity confirmed by existing tests + phpunit green.
