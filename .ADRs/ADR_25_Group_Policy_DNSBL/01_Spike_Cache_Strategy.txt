WHY THIS PHASE EXISTS
Per-client DNSBL verdicts have one genuine architectural hazard: Unbound's C message cache.
When a pass/warn client resolves a listed name, Unbound caches the REAL answer; a later
block client served from that C-cache never re-enters operate() and SILENTLY ESCAPES the
block. The whole feature is unsound unless this is solved with acceptable cost. Prove the
problem, pick a scheme on evidence, set a kill-threshold — BEFORE any code is built on top
(the ADR-01 lesson: validate the premise first).

ACTION PLAN (ordered)
1. REPRODUCE the bleed on a live VM (use the ADR-04 smoke VM): configure the LEGACY bypass
   (pfb_gp + pfb_gp_bypass_list) for one source IP; from a BYPASS source resolve a listed
   uuid-*.com name (warms the C-cache with the real answer); then from a NON-bypass source
   query the SAME name and observe whether it is (wrongly) served the real answer instead of
   the block shape. Drive distinct source IPs (drill -I <src>, a second interface, or source
   binding). Record the exact reproduction (commands + observed responses + unbound-control
   cache dump).
1b. REPRODUCE the SCHEDULE TIME-TRANSITION variant of the same bleed (ADR SS2.2): a
   policy-relevant name resolved while a group is OFF-schedule (verdict PASS) warms the
   C-cache with the real answer; when the schedule window opens the name should now BLOCK but
   may be served the stale cached answer and escape. Model the clock boundary (a short window,
   or a manual flip of "active now") and confirm whether the chosen scheme closes it. The
   group-policy feature folds in DNSBL-blocking-by-schedule (issue #384), so the cache scheme
   must hold across BOTH the client axis and the time axis.
2. EVALUATE candidate schemes from ADR SS2.2 (REVISED 2026-07-04 — re-read it first; the
   candidate set changed), each with a short written argument + a measured number where
   feasible:
   (a') PREFERRED CANDIDATE: divergence-gated no_cache_store — only names whose verdict can
        DIVERGE (across clients or time) skip the message cache; the build publishes a
        divergent mask; zero Client Groups => byte-identical caching. THE central number of
        this spike is (a')'s pass-path cost: a divergent listed name PASS-resolved per query
        — how far does Unbound's rrset cache bound the repeat cost (local assembly vs a
        network round-trip)? Also close the flush caveat: no_cache_store cannot evict an
        already-warm name — confirm the ADR-10 swap clear covers the policy-apply path, and
        prototype a targeted flush (unbound-control flush / flush_zone) for a schedule edge
        on a warm name.
   (a)  plain no_cache_store on every policy-relevant name — the degenerate simplicity
        baseline; measure it to quantify what (a')'s gating buys.
   (b)  LAST-RESORT FALLBACK (assess, do NOT build): a module-level RESOLUTION cache —
        stash qstate.return_msg at MODDONE keyed (qname,qtype,qclass), TTL-expiring,
        verdict-independent (per-client verdict applied on top at answer time). Enumerate
        the real complexity with evidence: DNSSEC (RRSIGs/security status preservation vs
        refuse-to-stash-validated), DO/CD flag variance in the key, re-running the
        per-client CNAME walk when serving from the stash. Numbers only as far as needed to
        judge whether it could rescue a failed (a').
   (c)  Unbound `views` + `access-control-view` (client CIDR -> view, per-view local data) —
        check feasibility AND memory at blocklist scale (this is why pfBlockerNG left
        local-zones); most likely reject WITH measured/estimated evidence.
3. BENCHMARK the viable candidate(s): warn/pass-client query latency on listed vs unlisted
   names (for (a'): divergent vs uniform vs unlisted), and memory vs #groups. Define
   METHODOLOGY (what is measured, how, sample size) and a KILL-THRESHOLD (e.g. "median added
   latency on divergent names > X ms, or memory > Y MB at N groups => fall back to (b) /
   reduce / reject").
4. DECIDE: pick the scheme Phases 3-7 will adopt, or recommend reducing scope (e.g.
   Bypass-only overrides — the shapes the surviving scheme supports) or rejecting this ADR's
   decision layer (ADR-54/55 stand regardless). State the decision and the numbers.
