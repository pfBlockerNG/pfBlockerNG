WHY THIS PHASE EXISTS
The cron-consolidation (Phase 4) needs a place to record "when is job/feed X next due" so a
single tick can decide what to run. Today only `.update`/`.last` last-run markers exist under
$pfb['dbdir']. Build the next-due ledger as a standalone, clock-injectable library FIRST, fully
tested, so Phase 4 wires a proven component. Two load-bearing facts drive the design:
  (a) $pfb['dbdir'] is on the MFS RAM disk on the issue-#468 reboot path → wiped on reboot
      unless persisted. ABSENT ledger MUST mean "due-now-but-jittered", never a stampede.
  (b) dcc/bl jitter (rand(0,23) today) is deliberate to spare upstreams → the ledger stores a
      STABLE seeded jitter offset, not a per-pass re-randomisation.

ACTION PLAN (oracle/unit tests FIRST — pure library)
1. Implement a due-ledger module (functions in pfblockerng.inc, or a small included file loaded by
   bootstrap.php — match how the codebase already factors helpers). Core API (names per house
   style), all CLOCK- and SEED-INJECTABLE (pass `now` epoch + a per-install seed; never call
   time()/rand() inside the pure core):
     - read_entry(job_key)  -> { last_run, next_due, jitter } | absent-sentinel
     - is_due(job_key, interval, now) -> bool   (absent ⇒ TRUE/“due-now-jittered”; next_due≤now ⇒ TRUE)
     - mark_ran(job_key, interval, now) -> persists last_run=now, next_due=now+interval(+stable jitter)
     - seeded_jitter(job_key, max) -> deterministic offset for a fixed (seed, job_key) — the dcc/bl spread
   Persist under $pfb['dbdir'] (atomic write, LOCK_EX), evolving — not duplicating — the existing
   `.update`/`.last` markers. Keep it a sidecar; NO config field.
2. WIRE IT INTO NOTHING. No cron change, no call from sync_package_pfblockerng. This phase only
   delivers the tested library + (optionally) a note in the handoff on how Phase 4 will use it.
3. Add PHPUnit tests (tests/php/) covering every branch:
     - absent entry ⇒ is_due TRUE with a NON-ZERO, STABLE jitter (same seed ⇒ same offset);
     - next_due in the future ⇒ not due; next_due in the past ⇒ due (catch-up);
     - a missed window ⇒ exactly ONE due (mark_ran advances next_due past now, no double-run);
     - round-trip read(write(x)) == x; corrupt/partial file ⇒ treated as absent (fail-safe due);
     - two different jobs get DIFFERENT stable jitters (no synchronised stampede).
