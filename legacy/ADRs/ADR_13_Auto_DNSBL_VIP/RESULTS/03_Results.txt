How the v6-required error is signalled
--------------------------------------
The requirement is decided by ONE pure function and surfaced by the existing validator:

  function pfb_dnsbl_v6_vip_required(bool $listens_v6, bool $auto): bool {
      return $listens_v6 && !$auto;     // required iff resolver listens v6 AND manual mode
  }

pfb_validate_vips($interface, $vip4, $vip6, ?bool $require_v6 = null):
  - $require_v6 === null (default)  -> the validator computes the requirement itself:
        $require_v6 = pfb_unbound_listens_v6();   // manual-mode semantics
    (pfb_unbound_listens_v6() is the Phase-1 predicate, verified vs upstream
    unbound_generate_config_text() at RELENG_2_7_2 + master.)
  - $require_v6 an explicit bool -> the CALLER decided (auto-mode callers pass false).
  - New branch, placed BEFORE the generic "no VIP configured" early return so the
    message is specific/actionable even when v4 is also absent:
        if ($require_v6 && !$enabled6) {
            return [false, gettext('IPv6 VIP required: the DNS Resolver is listening on IPv6')];
        }
  The branch returns the [bool, message] pair the validator already uses, so BOTH
  consumers pick it up with no extra wiring:
    * the DNSBL save handler pushes it as $input_errors[] = "DNSBL: {$error}"
      (manual-mode input error on Save), and
    * pfb_global() force-disables DNSBL on a false result (see next section).

The pfb_global() force-disable wiring
-------------------------------------
pfb_global() already force-disables DNSBL when pfb_validate_vips() returns false
(it sets $pfb['dnsbl'] = '' and logs the reason). Phase 3 makes the v6-missing case
ONE of the false results that path consumes — no new disable mechanism, just a new
trigger. The call site is made auto-aware:

    if (!empty($pfb['dnsbl'])) {
        $require_v6 = ($pfb['dnsbl_vip_auto'] === 'on') ? false : null;
        $vips_valid_result = pfb_validate_vips($pfb['dnsbl_iface'],
            $pfb['dnsblconfig']['pfb_dnsvip4'], $pfb['dnsblconfig']['pfb_dnsvip6'], $require_v6);
        if (!$vips_valid_result[0]) {
            $pfb['dnsbl'] = '';                                  // force-disable
            pfb_logger("\nDNSBL disabled: {$vips_valid_result[1]}", 1);
        }
    }

  - auto ON  -> require_v6 = false: the v6 rule is NOT enforced here, because
    pfb_manage_dnsbl_vip() (Phase 2) runs earlier on the SAME pass
    (pfb_create_dnsbl -> pfb_manage_dnsbl_vip BEFORE the NAT pass) and provisions the
    v6 VIP. Forcing the requirement would race the provisioner and falsely disable.
  - auto OFF (manual) -> require_v6 = null: the validator computes
    pfb_unbound_listens_v6(); a v6-listening resolver with no v6 VIP => false result
    => DNSBL force-disabled with the v6 message logged.
  ($pfb['dnsbl_vip_auto'] is set a few lines above to 'on'|'' — never null — so the
  === 'on' test is safe.)

Auto v6-provision branch is LIVE (confirmed)
--------------------------------------------
Phase 2's pfb_manage_dnsbl_vip() already provisions v6 when:
    $want_v6 = !empty($pfb['dnsblconfig']['pfb_dnsvip6']) || pfb_unbound_listens_v6();
    v6 family 'managed' = ($mode === 'enabled' && $auto && $want_v6);
So with the resolver listening on IPv6 AND auto on, $want_v6 is true and the v6 VIP
(fd00::53-style, marker pfB_AUTO_VIP_v6) is created + interface_ipalias_configure()'d
on the same enable pass, then pfb_global() is refreshed. The manager is called from
pfb_create_dnsbl($mode) BEFORE the NAT pass (Phase 2), so by the time pfb_global()
re-validates, the v6 id is stored. => Auto mode satisfies the new rule with zero user
friction. No Phase-3 change to the manager was needed; the branch was already wired.

Manual-mode decision: HARD INPUT ERROR (mandatory) — kept, with rationale
-------------------------------------------------------------------------
DECISION: implement the default = a hard input error / force-disable (NOT the softened
warning). Implemented exactly ONCE (the single $require_v6 && !$enabled6 branch); the
softened-warning pivot is NOT shipped.

Rationale (evidence the disruption is narrow and recoverable):
  - The rule fires for a TIGHTLY bounded population only: DNSBL enabled AND resolver
    listening on IPv6 AND no v6 VIP AND manual mode. v4-only setups, IPv6-disabled
    resolvers, and auto-mode users are all untouched.
  - The predicate is conservative (Phase 1): resolver disabled => false; automatic-bind
    => true only if the box actually has a v6 interface address; explicit list => true
    only on a real v6 literal/interface. It does not over-fire on link-local-only or
    v4-only boxes.
  - Compliance is one click: turning on "Create VIPs automatically" (Phase 4) makes the
    package provision the v6 VIP, clearing the error with no manual VIP creation.
  - This lands on devel (the development/pre-release channel), the correct place to take
    a documented behaviour change; it closes the real correctness gap the ADR calls out
    (a blocked AAAA with no v6 sinkhole). The ADR's softening lever (§7) remains
    available if field reports show it is too disruptive — flipping the default is a
    one-line change (return a warning instead of an input_error/force-disable).

No-regression argument (non-v6-listening cases are byte-identical)
------------------------------------------------------------------
The new branch is `if ($require_v6 && !$enabled6)`. $require_v6 is false in EVERY
non-v6-listening case:
  - manual mode (require_v6 = null): the validator computes pfb_unbound_listens_v6(),
    which is false when the resolver is disabled / has no v6 interface -> branch skipped.
  - auto mode (require_v6 = false): branch skipped unconditionally.
With the branch skipped, control falls through to the IDENTICAL pre-Phase-3 code:
the "no VIP configured" early return, the v4/v6 interface checks, and the
where_is_ipaddr_configured overlap checks are unchanged. v6 stays OPTIONAL exactly as
before. The two new pfsense_doubles are function_exists()-guarded and only resolve the
new tests' sentinel ids — no production path change.

Full matrix {resolver v6 on/off} x {auto on/off} x {v6 VIP present/absent}
--------------------------------------------------------------------------
  v6off, auto off, absent  -> require_v6=false  -> v6 optional, unchanged ("no VIP" only if v4 also absent)
  v6off, auto off, present -> require_v6=false  -> unchanged
  v6off, auto on,  absent  -> require_v6=false  -> no v6 error; manager provisions nothing v6 (want_v6 false)
  v6off, auto on,  present -> require_v6=false  -> unchanged
  v6on,  auto off, ABSENT  -> require_v6=true   -> *** v6-required ERROR + force-disable ***  (ONLY new failure)
  v6on,  auto off, present -> require_v6=true   -> rule cleared (v6 present), normal validation
  v6on,  auto on,  absent  -> require_v6=false  -> no error; manager PROVISIONS the v6 VIP (want_v6 true)
  v6on,  auto on,  present -> require_v6=false  -> no error; normal validation
=> The single new failure path is (v6-listening, no v6 VIP, manual mode). Auto mode
   provisions the v6 VIP (no friction). Every non-v6-listening row is byte-identical.
