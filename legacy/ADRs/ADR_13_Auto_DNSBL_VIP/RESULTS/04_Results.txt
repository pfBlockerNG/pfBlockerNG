How the prefill address is computed + passed to JS
--------------------------------------------------
Server-side, at render, against the SELECTED Web Server interface ($pconfig['dnsbl_interface']):
    $pfb_auto_iface    = $pconfig['dnsbl_interface'] ?: 'lo0';
    $pfb_auto_v6_needed = pfb_unbound_listens_v6();                       // Phase 1 predicate
    $pfb_auto_vip4     = pfb_pick_free_dnsbl_vip(AF_INET,  $pfb_auto_iface);  // ?string
    $pfb_auto_vip6     = $pfb_auto_v6_needed ? pfb_pick_free_dnsbl_vip(AF_INET6, $pfb_auto_iface) : null;
pfb_pick_free_dnsbl_vip() (Phase 1) returns the first free 10.10.X.53 / fd00:X::53 candidate
(null when every candidate conflicts). The two addresses are emitted to JS as escaped string
literals (htmlspecialchars(..., ENT_QUOTES); '' when null/not-needed):
    var pfb_auto_vip4 = "<?=htmlspecialchars($pfb_auto_vip4 ?? '', ENT_QUOTES)?>";
    var pfb_auto_vip6 = "<?=htmlspecialchars($pfb_auto_vip6 ?? '', ENT_QUOTES)?>";

Disable/restore JS behaviour (enable_dnsvip_auto)
-------------------------------------------------
Matches the page's existing inline-jQuery toggle idiom (the enable_*()+'.click()'+init pattern
used for pfb_tld / dnsbl_interface / pfb_pytld / ...). For each of pfb_dnsvip4 / pfb_dnsvip6:
  ON check :
    - remember the manual selection once: $sel.data('pfbManualVal', $sel.val()) (idempotent),
    - remove any prior synthetic option, then (if an address is available) append a synthetic
      <option class="pfb-auto-opt" value="_pfb_auto">ADDRESS</option> and select it (display),
    - disableInput(id, true) (pfSense global helper -> .prop('disabled', true)).
  OFF uncheck:
    - disableInput(id, false), remove the synthetic option, restore the remembered manual
      selection ($sel.val(pfbManualVal)) and drop the saved value.
Wired in events.push: $('#pfb_dnsvip_auto').click(enable_dnsvip_auto); enable_dnsvip_auto();
so the page is in the correct state on load and on every toggle. Per-interface: the prefill
addresses are computed for the selected dnsbl_interface at render time.

Why a DISABLED select is the linchpin of the save wiring
--------------------------------------------------------
disableInput sets the DOM 'disabled' property, and a disabled form control is NOT submitted.
So when auto is ON and the form is saved, $_POST carries NO pfb_dnsvip4 / pfb_dnsvip6 (and the
synthetic '_pfb_auto' sentinel never reaches PHP). The POST handler therefore never sees a bad
id; it skips the manual VIP validation and skips saving those ids entirely. The actual VIP +
the real _vip{uniqid} ids are provisioned server-side on the next pfb_create_dnsbl('enabled')
pass (pfb_manage_dnsbl_vip, Phase 2), which repoints pfb_dnsvip4/6.

Exhausted-conflict treatment (admin cannot enable auto)
-------------------------------------------------------
    $pfb_auto_exhausted = ($pfb_auto_vip4 === null) || ($pfb_auto_v6_needed && $pfb_auto_vip6 === null);
v4 is always required; v6 only when the resolver listens on IPv6. When exhausted:
  - the checkbox is rendered DISABLED ($chk->setAttribute('disabled','disabled')) and unchecked
    (the checked expression ANDs in !$pfb_auto_exhausted) -> the admin cannot enable auto-create
    into a known-conflicting state, per the phase requirement;
  - its help gains the STOCK warning: <i class="fa fa-exclamation-triangle text-warning"
    data-toggle="tooltip" title="No free address ... Free one ... or create a DNSBL VIP manually
    at Firewall > Virtual IPs"></i> plus a text-warning <span> with the same guidance. No custom
    CSS/markup; pfSense's global tooltip init handles data-toggle="tooltip".

Save wiring (auto-on relaxes manual validation, KEEPS the v6 rule)
-----------------------------------------------------------------
  $pfb_auto = (isset($_POST['pfb_dnsvip_auto']) && $_POST['pfb_dnsvip_auto'] == 'on');
  POST validation:
    - auto OFF -> run pfb_validate_vips($iface, $vip4, $vip6) with require_v6 DEFAULT (null) ->
      the validator computes pfb_unbound_listens_v6() live, so a v6-listening resolver in manual
      mode STILL requires a v6 VIP (Phase-3 rule INTACT, unchanged from before this phase).
    - auto ON  -> SKIP the manual VIP validation block entirely. Rationale: the manual dropdowns
      are disabled (no values submitted) and the package owns provisioning — it picks a
      conflict-free address and provisions the required v6 VIP itself (pfb_manage_dnsbl_vip on
      the next enable pass; pfb_global passes require_v6=false in auto mode, Phase 3). The v6
      rule's machinery is untouched; it is correctly suppressed for auto (the package satisfies
      it), not deleted.
  Persist:
    - $pfb['dconfig']['pfb_dnsvip_auto'] = $pfb_auto ? 'on' : '';   (always)
    - pfb_dnsvip6 / pfb_dnsvip4 saved from POST ONLY when !$pfb_auto (manual mode). In auto mode
      the stored ids are left untouched here for the manager to reuse/repoint.
