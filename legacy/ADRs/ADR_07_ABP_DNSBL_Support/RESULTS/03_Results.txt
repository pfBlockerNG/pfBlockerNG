2. THE important_rules FAST PATH — how it gates old vs numeric resolution
================================================================================
evaluate_domain discovery (data -> zone -> tld-allow -> idn -> block-regex) is
UNCHANGED in order/semantics; it now also records the matched block's `important`
into a local `block_important` (False on the fast path). The RESOLUTION stratum
then branches:

  if is_found:
      if not cfg.get("important_rules", False):     # FAST PATH (today)
          if cfg["whiteDB"]:
              in_whitelist = any(whitelist_check_domain(n, ...) for n in names)
      else:                                          # NUMERIC 6-BAND (unreachable)
          in_whitelist = _resolve_numeric_allow(...)

* FAST PATH is byte-for-byte the pre-P3 matcher: `if is_found: if not flag: if
  cfg["whiteDB"]:` == old `if is_found and cfg["whiteDB"]:`. allowRegexDB is NOT
  consulted; the `important` fields are NOT read for the decision. THIS is the
  no-regression guarantee — confirmed by the ADR-06 oracle and
  TestFastPathPreserved (incl. flag-key-absent and important-block-ignored cases).
* NUMERIC branch (_resolve_numeric_allow): computes block_prio vs allow_prio and
  returns True (== "in_whitelist", i.e. an ALLOW overrides -> name resolves) iff
  allow_prio >= block_prio (no ties, so equivalent to NOT(block_prio>allow_prio)
  = the ADR rule "block wins iff block_prio > allow_prio"). Maps the allow-wins
  result onto in_whitelist so the downstream hsts/null-blocking/CNAME logic is
  SHARED with the fast path (DnsblDecision external shape unchanged).

cfg keys consumed: cfg["important_rules"], cfg["allowRegexDB"], cfg["whiteDB"]
(all via fast/numeric branch). Phase 6 must thread these into the operate()-built
cfg (the build emits the flags; init copies into pfb[...] -> cfg).
