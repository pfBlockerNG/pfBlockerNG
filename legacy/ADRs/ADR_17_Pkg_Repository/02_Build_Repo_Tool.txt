ROLE
You are on the `adr/17` branch performing Phase 2 of ADR-17. Build the reusable,
deterministic tool that turns a directory of `.pkg` files into a per-ABI `pkg`
repository tree plus the client repo-conf template. Work in this ADR's `adr/17`
worktree, one commit.

WHY THIS PHASE EXISTS
Phase 1 hand-assembled a throwaway single-ABI catalog to prove the box honors it.
Phase 3's CI must do this faithfully for ALL published ABIs, every deploy, on a Linux
runner. This phase makes catalog generation a single proven, lint-clean script — and
settles the build-side premise: is a libpkg-on-Linux catalog accepted by a real
pfSense `pkg update`, or do we need the FreeBSD-VM fallback?

ACTION PLAN (ordered)
1. `scripts/build-repo.sh` (POSIX sh): inputs = a dir of `.pkg` + an output dir. Bucket
   each `.pkg` by its ABI (read from the package, do not guess), lay out `…/<ABI>/` with
   the `.pkg` under it, and run `pkg repo <…/<ABI>>` to emit `meta.conf`/`packagesite.pkg`/
   `data.pkg` per ABI. Deterministic; re-runnable; no network.
2. FLAVOR-COLLISION GUARD: if two inputs share package-name + version + ABI but differ in
   php/py flavor (so they cannot coexist in one catalog), FAIL LOUD with a clear message
   (never silently drop a build). Document the future split (`…/<ABI>-<php><py>/`) in a
   comment; do NOT implement the split now (no colliding combo exists today — CE 2.8 +
   Plus 25.03 are both FreeBSD15/php83/py311).
3. Emit the client repo-conf TEMPLATE (a file under scripts/ or a heredoc the script can
   print): `url:` using the `${ABI}` variable + a STATIC base (no query interpolation),
   `mirror_type: none`, `signature_type: none`, `priority:` above the pfSense repo,
   `enabled: yes`. This is the single source Phase 4's `add-repo.sh` and the README share.
4. SETTLE THE BUILD-SIDE PREMISE: generate a catalog with the Linux libpkg and confirm a
   real pfSense VM `pkg update` accepts it (reuse the Phase-1 VM path). If it is rejected,
   wire the FreeBSD-VM fallback (the `build-pkg.yml` env already exists) and record which
   path Phase 3 must use. Record the decision + evidence in the handoff.
5. Local validation: a tiny fixture run (a couple of dummy `.pkg` or the Phase-1 `.pkg`)
   that produces a valid tree; show the resulting layout in the handoff.

CONSTRAINTS
- POSIX sh, `#!/bin/sh`, quoted expansions, absolute binary paths; ShellCheck-clean
  (justify any suppression). No bash-isms.
- The conf URL is STATIC (the URL-encoding gate scans tracked shell + md fences).
- Do NOT add the CI job (Phase 3), `add-repo.sh` (Phase 4), or touch `src/`.
- Reuse the matrix shape; do NOT modify ADR-09's matrix or builders.

VERIFICATION (must all pass before the phase is done)
- shellcheck scripts/build-repo.sh + `sh -n` → clean; the URL-encoding gate
  (scripts/check_url_encoding.py) → clean on the new shell.
- A local run produces a valid `…/<ABI>/` tree with the three catalog files; a real VM
  `pkg update` against it succeeds (or the FreeBSD-fallback decision is recorded).
- python -m pytest (default) → unchanged.

EXPECTED RESULT
`scripts/build-repo.sh` deterministically generates a per-ABI `pkg` catalog with a
loud collision guard, plus the shared `${ABI}`/`none` repo-conf template — and the
libpkg-on-Linux vs FreeBSD-fallback question is answered with evidence.
