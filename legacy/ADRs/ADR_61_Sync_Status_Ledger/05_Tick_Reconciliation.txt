WHY THIS PHASE EXISTS
Phases 2-3 make apply-stage failures VISIBLE (ledger entries) but nothing retries them --
today's system leaves a stuck pfctl/DNSBL apply broken until the source changes or an
operator Force-Reloads. This phase makes pfblockerng_tick() close that gap for the
apply stage ONLY, per direct instruction: every tick, unconditionally, unbounded retry
count, no backoff.

ACTION PLAN (ordered)
1. Add one new, unconditional step inside pfblockerng_tick() (fires every call, NOT
   gated on $due[...] or pfb_due_ledger_is_pending(...) -- this is the whole point):
   read pfb_sync_status_list_open($dbdir) filtered to stage='apply'. Nothing else in the
   ledger (download/parse entries) is touched by this step (Semantics #5).
2. For each open IP apply-stage entry: re-invoke pfb_apply_alias_delta() (or the
   narrower operation Phase 2 identified) against the ALREADY-PERSISTED mirror/canonical
   set for that alias -- no re-download, no re-parse, no re-dedup. On success, the
   Phase-2 clearer already fires naturally if you're calling through the same code path;
   if not, call pfb_sync_status_close() explicitly here. On failure, leave the entry
   open (it retries again next tick -- no counter, no backoff, per SS2.4).
3. For each open DNSBL apply-stage entry: call pfb_dnsbl_converged() (Phase 3). If FALSE,
   re-attempt whatever Phase 3's RESULTS identified as the retry-safe operation (the
   sentinel-flip/wait-applied/restart sequence, scoped to NOT re-download/re-parse
   anything -- it is re-publishing/re-confirming already-known-good manifest state). If
   TRUE, close the entry.
4. Keep this step SYNCHRONOUS and cheap (SS2.4: "no network I/O, no feed re-parse") --
   if either retry operation turns out to require something heavier than that in
   practice, STOP and escalate in the handoff as a contradicted premise (per CLAUDE.md's
   ESCALATE contract) rather than silently backgrounding it, which would break the
   "closes within one tick interval" acceptance criterion (ADR SS4 item 4).
5. Verify the $dispatched flag / log-maintenance race guard is genuinely unaffected --
   read TickEntrypointTest's Case D and confirm this new step does not run inside any
   region that could interact with it; add a regression assertion if a plausible
   interaction exists.

- Do NOT modify the widget (Phase 6).
