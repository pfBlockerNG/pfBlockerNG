DEVIATIONS / JUDGMENT CALLS

1. `$pfb['config'][...]` vs `PfbConfig::read()`: used `$pfb['config']
   ['log_max_days_' . $logtype]` (matching the sibling `log_max_` read

2. 'nolimit'-with-no-line-cap-candidate: read the WHOLE file via PHP's
   `copy($final_log_file, $temp)` (a plain filesystem copy, not a shelled-out
   `cp`) rather than an exec(). This is the ADR's suggested approach (S2.2:
   "reading the WHOLE file... is the ADR's suggested approach"). Chose
   `copy()` over `exec("/bin/cp ...")` -- shortest correct diff, no new
   shell-quoting surface for a plain file-to-file copy PHP's stdlib already
   does natively; its boolean return still gates the SAME downstream
   failure-protection logic (`$ret = 1` on failure) as the tail exec's exit
   code. Not a duplicated chroot/chown code path -- the chown/chgrp step is
   still the SAME single call site, reached only after the final cat exec.
3. Did NOT factor a separate shared chroot/ownership helper -- the existing
   chroot/non-chroot branching in pfb_log_mgmt() was left structurally
   intact (two branches, as before); only the CANDIDATE-PRODUCTION step
   (tail vs copy) and an inserted age-trim gate were added inside each,
   without touching the final cat/chown/logging code at all in either
   branch. This kept the diff to insertions only in the "produce the
   candidate" section, avoiding any risk of introducing a behavioural
   difference in the chroot-specific ownership logic.
4. Timestamp parsing: `DateTime::createFromFormat('Y-m-d H:i:s', ...)` PLUS
   a strict round-trip check (`$dt->format(...) === $candidate`) PLUS a
   `DateTime::getLastErrors()` warning/error check -- validated via an
   independent probe this session (pasted above) that createFromFormat()
   alone is too lenient. A `strlen($candidate) !== 19` pre-check also guards
   against createFromFormat()'s tolerance for a missing literal separator in
   a shorter string (independently probed: a merged "2026-07-0814:30:00"
   with no space parses "successfully" under this format at 18 chars --
   the length check rejects it before createFromFormat() is even called).
5. The generic "failed to tail {file} for truncation" log message is reused
   verbatim for BOTH the tail-exec failure AND the new copy()-failure case
   (the 'nolimit' branch) -- a minor, rare-path cosmetic wording inaccuracy
   (an operator would see "failed to tail" even when no tail ran), left
   as-is: correcting it would only touch a log string, not behaviour, and
   copy() failing implies the same tmp-dir-unwritable condition that would
   equally break the tail-exec path in the numeric-cap case.
None of the above weakens any CLAUDE.md MUST rule.
