DEVIATIONS / JUDGMENT CALLS
--------------------------------------------------------------------------------
1. The brief offered a choice for pfb_log_event()'s test coverage: drive it
   for real, or fall back to Phase 1's "source tripwire + formula
   reproduction" convention if disproportionate mocking would be needed. I
   drove it for real. The one nuance discovered during construction:
   pfb_log_event()'s "not duplicate" branch has a PRE-EXISTING, out-of-scope
   bug -- `$req_agent = $data[2];` reads an undefined array offset, because
   pfb_dnsbl_parse('daemon', ...) only ever returns a 2-element array
   (`array($pfb_group, $details)`). Calling pfb_log_event() down that branch
   would raise an unrelated PHP warning having nothing to do with this
   phase's timestamp change, and touching it would be scope creep (the brief's
   constraint: "only the timestamp string's format"). Resolved by pre-seeding
   the lastevent SQLite row so pfb_log_event() takes its OTHER branch (the
   "duplicate entry" path, which never calls pfb_dnsbl_parse()) -- a
   legitimate, real production code path (a repeat block of the same
   domain+src_ip), not a workaround around the function's real behaviour.
   This exercises the REAL pfb_log_event() function, unmodified, with zero
   mocking of it. Not filed as a new tracking issue: it is pre-existing,
   unrelated to any log-timestamp ADR, and out of this phase's stated scope;
   flagged here for visibility per CLAUDE.md's finding-transparency rule.
2. Widened the unilog re-verification beyond the brief's own framing: the
   brief said "re-verify unilog's python-row passthrough" without
   distinguishing that Phase 3's carry-forward was about IP rows
   (pfb_unified_format_ip()) while Phase 4's own dnslog/dnsreplylog writers
   feed a DIFFERENT pair of formatters (pfb_unified_format_dnsbl()/
   pfb_unified_format_dnsreply()) that neither this phase's brief nor Phase
   3's carry-forward had tested with an ISO-shaped fixture. Added the two
   UnifiedFormatTest.php cases above to close that gap for real, rather than
   silently reusing Phase 3's IP-row verification as if it covered this
   phase's own writers too.
None of the above weakens any CLAUDE.md MUST rule.
