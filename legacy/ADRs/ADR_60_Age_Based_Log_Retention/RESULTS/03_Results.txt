DISCREPANCY FOUND AND RESOLVED (not silently patched -- documented here):
Applying the literal ">6h in the future" rollback check to the brief's OWN
"Jul 4 relative to a Jan 5 $now" example ALSO triggers a rollback (Jul 4 is
~6 months after Jan 5, which is obviously >6h in the future), producing
2025-07-04, not the raw-parsed 2026-07-04. The brief's own probe notes
anticipate exactly this and explain it away: pfb_daemon_filterlog() is a
LIVE-tailing daemon, so a BSD line's month is always close to "now" in
production; a many-months-away BSD line is outside this heuristic's design
domain (same accepted limitation any yearless-BSD-syslog scheme has), not a
bug to fix. I treat this as CONFIRMED, not a contradiction requiring
BLOCKED, because:
  (1) the brief itself calls out this exact input class as out-of-domain,
  (2) the REAL hostile-input row the brief specifies (item 5b: "a line
      timestamped for 'today' relative to $now") is a near-$now case, where
      the naive parse is NOT months away and the future-check correctly
      does NOT fire -- verified below.
Same-day probe (the realistic daemon case):
$ php -r '
date_default_timezone_set("UTC");
$now = strtotime("2026-07-08 10:00:00 UTC");
$ts = strtotime("Jul 8 07:00:00", $now);
echo (($ts > $now + 6*3600) ? "ROLLBACK" : "NO-ROLLBACK") . " " . date("Y-m-d H:i:s", $ts) . "\n";
'
NO-ROLLBACK 2026-07-08 07:00:00   (correct: "today" picks the current year)

December-read-in-January probe (the classic rollback case):
$ php -r '
date_default_timezone_set("UTC");
$now = strtotime("2026-01-05 10:00:00 UTC");
$ts = strtotime("Dec 31 23:00:00", $now);
echo (($ts > $now + 6*3600) ? "ROLLBACK" : "NO-ROLLBACK") . "\n";
$ts2 = strtotime("Dec 31 23:00:00 " . ((int) date("Y", $now) - 1), $now);
echo date("Y-m-d H:i:s", $ts2) . "\n";
'
ROLLBACK
2025-12-31 23:00:00   (correct: rolls back exactly one year)

Malformed-field probe:
$ php -r '
date_default_timezone_set("UTC");
var_dump(strtotime("Foo 99 99:99:99", time()));
'
bool(false)   (fallback to pfb_log_iso_timestamp() engages, confirmed no warning
              -- see hostile-input row (d) below, which asserts this via
              set_error_handler())

CONCLUSION: the algorithm as specified in the brief is CONFIRMED correct for
its stated design domain (near-$now BSD lines, the only case a live-tailing
daemon actually produces); the far-future edge is a documented,
brief-acknowledged limitation, not a defect. No BLOCKED, no silent
adjustment of the tolerance/algorithm -- wired exactly as specified.
