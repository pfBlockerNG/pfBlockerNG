DEVIATIONS / JUDGMENT CALLS
--------------------------------------------------------------------------------
1. pfb_daemon_filterlog()'s 'BSD'/'syslog' timestamp branch (the ip_blocklog/
   ip_permitlog/ip_matchlog row) is NOT directly unit-callable: the function
   opens php://stdin and loops `while (!feof($s_handle))` reading lines from
   a live/piped filter.log tail — there is no extracted pure helper for this
   branch (unlike pfb_filterlog_port()/pfb_filterlog_skip_count(), which WERE
   extracted in a past issue specifically for testability — confirmed via
   FilterlogPortTest.php/FilterlogSkipCountTest.php). The brief's CONSTRAINTS
   authorize exactly two new helpers (pfb_log_iso_timestamp/iso_timestamp)
   and explicitly says not to change any existing log's OUTPUT; extracting a
   third helper for this branch was judged out of this phase's authorized
   scope (ADR.md's own Phase 3 description keeps the rewrite "in one output
   path" inside pfb_daemon_filterlog() without mentioning an extraction
   either — Phase 3 will need to build whatever testable seam its own
   red-before/green-after proof requires).

   Given that, these two rows are pinned via (a) a grep TRIPWIRE asserting the
   exact current source line is still present verbatim (so this oracle goes
   RED the instant Phase 3 changes that line — verified: the three tripwired
   substrings were confirmed present in the live source via a byte-exact
   Python `in` check before writing the tests, not assumed) plus (b) a
   reproduction of that exact formula against synthetic BSD/RFC-5424
   fixtures. This is weaker evidence than driving the real function, but the
   tripwire half gives it genuine discriminating power for Phase 3's
   red-before proof (it WILL fail once pfb_daemon_filterlog()'s formula
   changes), which a pure formula-reproduction alone would not.
   CARRY-FORWARD for whoever plans Phase 3: decide whether to (i) rewrite
   these two tests to call a newly-extracted formatter function once Phase 3
   creates one (mirroring how Phase 2 is told to rewrite
   PfbLoggerIsoTimestampTest.php's dedup assertions), or (ii) keep the
   tripwire+reproduction shape and just flip the expected format. Either is
   valid; flagged here so it isn't missed.

2. The same-second dedup tests (testLogNowTokenStrippedToNothingWhenPnow...,
   testPnowDedupContaminatesAcrossLogAndExtrasLog,
   testErrlogAlwaysStampedEvenWhenMainLogDedupStripsTimestamp) have an
   inherent race: pfb_logger() computes `date('Y-m-d H:i:s', time())`
   internally with no injectable clock, so the test can only PRESET
   $pfb['pnow'] to a timestamp computed just before the call and hope the
   wall-clock second does not roll over in between. Mitigated with a bounded
   (5-attempt) retry helper (runWithinSameSecond()) that re-verifies
   before/after equality and asserts loudly if every retry crossed a
   boundary, rather than silently passing on a false premise. This is a
   test-infrastructure judgment call, not a production-code compromise.

3. date_default_timezone is saved/set to 'UTC' and restored in
   setUp()/tearDown() of LogTimestampBaselineTest, so the syslog-branch
   reproduction test (which reformats a fixed instant with an explicit
   timezone offset) is not flaky under a CI runner with a non-UTC system
   timezone. Verified the bootstrap does not already pin this (grepped
   tests/php/bootstrap.php — no date_default_timezone_set call there).

None of the above weakens any CLAUDE.md MUST rule; both are documented
test-infrastructure choices for otherwise-untestable/racy production code.
