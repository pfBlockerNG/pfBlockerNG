PER-LEG RE-RUN ISOLATION (the D1 requirement — explained):
  Each (tier x version) is a SEPARATE GitHub job (the matrix in ui-tests.yml's
  `ui` job, fail-fast: false). `release` runs only once ALL of its `needs:` are
  `success`. Therefore:
    - A single flaky leg (e.g. browser/ce) fails -> `release`/`ports-pr` do NOT
      run (their needs aren't all green) and the OTHER legs are NOT cancelled
      (fail-fast: false).
    - "Re-run failed jobs" re-runs ONLY that one leg. When it goes green, the
      `needs:` set becomes all-success and `release`/`ports-pr` proceed — WITHOUT
      re-running the passing legs and WITHOUT redoing any already-done publish
      step. A not-our-fault browser flake costs a single-leg re-run, never a
      republish.
  This is the GitHub-native mechanism; it is STRUCTURAL (the job-per-leg + the
  needs graph), proven by the parsed YAML, and confirmed live by the maintainer's
  §7 "Release dry-run" checklist item (forced single-leg failure, re-run in
  isolation). NO dry-run was claimed to have "run" here (this box can't run GHA).

§7 BROWSER DEMOTE SWITCH (decision + how):
  DECISION: gate the release on Tier A + Tier B-functional FIRMLY and INCLUDE the
  browser leg as a separate, isolated, re-runnable leg (`tier: all`). Rationale:
  the browser tier is already non-PR-blocking BY CONSTRUCTION (Phase 4 §6), so
  including it in the release gate adds JS/screenshot coverage at the cost of one
  re-runnable leg; its §7 numbers are CI-pending and the maintainer applies the
  switch on the FIRST CI evidence if it misses the bar.
  ONE-LINE DEMOTE (documented inline in release.yml's ui-suite header + in ADR §7):
    (a) drop `browser` from DEFAULT_SCHEDULE_TIERS in ui-tests.yml (kills the
        nightly browser leg), AND
    (b) change `tier: all` -> `tier: functional` in release.yml's ui-suite
        (drops browser from the release gate).
  The browser stays dispatch-only; the test code is untouched; Tiers A + B-HTTP
  keep gating the release.
