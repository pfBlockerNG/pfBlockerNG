WHY THIS PHASE EXISTS
The DNSWL feature rests on one existing fact: a feed-level allow (band 2, the shape
an ABP `@@||host^` rule already produces) overrides a block feed (band 1) but loses
to the operator's manual whitelist (band 6). Phase 2 will route permit-feed hosts
into that SAME band-2 store. So we first pin band-2 semantics as an ORACLE that must
already be green on untouched devel — it becomes the regression net proving Phase 2
did not disturb existing ABP allow behaviour and that the operator still wins.

ACTION PLAN (tests only)
1. Using the existing off-box build harness, construct a manifest with TWO feeds:
   a block feed listing host H, and a feed carrying an ABP allow `@@||H^`.
2. Pin, before-and-after (this is the band-2-beats-band-1 contract):
   - block feed only  -> H is BLOCKED (is_found true / block decision).
   - block + @@ allow  -> H RESOLVES (allow wins; band 2 >= band 1).
3. Pin operator sovereignty (the safety contract Phase 2 must not break):
   - manual suppression entry for H  -> H RESOLVES even with a block feed (band 6).
   - the @@ allow (band 2) does NOT override a manual `$important` user block
     (band 5) — assert the block still wins. (Read the bands; if no easy band-5
     fixture exists, assert at least that band-6 manual whitelist is sovereign and
     document the band-5 case for the smoke phase.)
4. Pin non-interference: a non-listed host is unaffected in all cases.
   Name tests BDD-style for the behaviour (Given block feed + @@ allow / When
   resolving H / Then resolves). Comments state INTENT, not mechanics.
