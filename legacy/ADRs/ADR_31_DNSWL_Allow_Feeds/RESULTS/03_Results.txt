Deny manifest-entry decision
-----------------------------
Decision : **OMIT** ``mode`` for deny rows (default ``$mode = 'deny'`` and explicit
           ``'deny'`` both omit the key).

Rationale: Phase 2 confirmed that absent == deny in Python (``feed_row.get("mode") ==
           "permit"`` is the only branch; absent/deny both fall through to the existing
           block path). Omitting the key keeps every existing deny-row manifest entry
           byte-identical — no diff in the written JSON, no churn in existing installs.

Pinned by: ``tests/php/FeedManifestRowTest.php`` — tests
           ``testDenyRowOmitsModeKey`` and ``testExplicitDenyRowOmitsModeKey``
           assert ``assertArrayNotHasKey('mode', $row)`` for both the default and
           explicit deny cases (both sides of the branch).

What Phase 4 must pass to stage a permit row
--------------------------------------------
Phase 4 (DNSWL section wiring) must:

1. Iterate ``config_get_path('installedpackages/pfblockerngdnswl/config', [])`` rows
   (a new config section, parallel to pfblockerngdnsbl/config; dynamic per-row,
   foreign/section-level — do NOT register in PfbConfig).

2. For each enabled row, call the existing DNSBL download/stage machinery exactly
   as the deny loop does (pfb_download → .orig staging, .bk parsing, .txt rename,
   .abp marker) — THEN call::

     $pfb_py_feeds[] = pfb_feed_manifest_row(
         $header, $alias, $logging_type,
         $easylist ? 'abp' : 'plain',
         $custom   ? 'user' : 'feed',
         'permit'          // ← the ONLY new argument vs the deny loop
     );

3. The resulting manifest entry will carry ``"mode": "permit"`` — exactly the JSON
   token the Phase-2 Python branch checks (``feed_row.get("mode") == "permit"``).

4. ``pfb_unbound_python_sources()`` consumes the ``$pfb_py_feeds[]`` array unchanged;
   Phase 4 adds permit rows to the same array before the call at pfblockerng.inc:12053.

The PFBL-01 validation contract applies identically: the permit section's download loop
must call ``pfb_filter($header, PFB_FILTER_WORD, ...)`` and/or
``pfb_sanitise_feed_header()`` before any exec/path/json_encode derived from $header —
same posture as the deny loop. Add ``pfb_feed_manifest_row`` to ``scopeFunctions`` in
RequirePfbFilterSniff.php only if the new function itself needs to become an in-scope
surface (currently it does not — it contains no exec or path derivation).
