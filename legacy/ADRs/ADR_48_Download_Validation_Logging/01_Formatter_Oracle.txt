WHY THIS PHASE EXISTS
Every download-validation reject site currently emits an ad-hoc string, so an
operator cannot grep one canonical line for "why was this feed rejected?" and
the raw file(1) output is not recorded next to the failing stage (#581). This
phase lands the canonical formatter + emit wrapper, fully unit-tested; Phase 2
wires the call sites.

ACTION PLAN (ordered)

1. Add the pure formatter to pfblockerng.inc (end of the pure-helper block):

       function pfb_validate_log_line(string $feed, string $stage, string $reason, string $detail = ''): string

   Canonical output (single line, leading "\n" per the pfb_logger caller
   convention, all four keys ALWAYS present — empty detail still prints
   `detected=`):

       \npfb_validate: REJECT feed=<feed> stage=<stage> reason=<reason> detected=<detail>

   Escaping — applied to EACH of the four values independently, in this order:
   a) neutralise control characters: replace every byte in [\x00-\x1F\x7F]
      with a single space (these values include attacker-influenced file(1)
      output; a raw \n or \r would forge/split the greppable line — ADR §7
      reject criterion);
   b) htmlspecialchars() (match the escaping the existing reject messages use,
      e.g. pfblockerng.inc L1275).
   Pure function: string in, string out, no I/O, no globals.

2. Add the thin emit wrapper right below it:

       function pfb_validate_log(string $feed, string $stage, string $reason, string $detail = '', int $level = 2): void

   Body: pfb_logger(pfb_validate_log_line($feed, $stage, $reason, $detail), $level);
   Nothing else. Default level 2 = pfB + error log (the reject level).

3. NO call-site changes anywhere. Phase 2 owns the wiring.

(#[CoversFunction('pfb_validate_log_line')]), oracle style:
