WHY THIS PHASE EXISTS
ADR-18 has no perf claim, but it has two unproven `pkg`-mechanics premises (§1). If a
real box does NOT order dated versions monotonically, or will NOT let a separately
named `-NIGHTLY` package replace an installed `-devel` across a conflict, the design
is wrong and must be reshaped BEFORE the build/publish pipeline exists (the ADR-01
guard: falsify the premise first). This phase settles both with a hand-built nightly
`.pkg` and a hermetic `file://` catalog — no builder change, no CI.

ACTION PLAN (ordered — transition asserts, both branches)
1. Build/obtain the branch `.pkg` once (the harness already builds it for the `repo`
   flow). Produce THREE hand-made nightly variants by repacking just the manifest
   (`+MANIFEST`/`+COMPACT_MANIFEST`) of that `.pkg`: set `name` =
   `pfSense-pkg-pfBlockerNG-NIGHTLY`, `conflicts` =
   `[pfSense-pkg-pfBlockerNG, pfSense-pkg-pfBlockerNG-devel]`, and `version` =
   `20260605`, `20260606`, `20260606.000001` respectively. Keep everything else
   identical (same files/deps), so the only variables are name/version/conflicts. Do the
   repack in-test (Python tarfile/zstd via the guest, or `pkg create` on the VM from an
   unpacked+edited manifest) — NO change to scripts/.
2. CONFLICT-AND-REPLACE (both directions), as a transition:
   - GIVEN `-devel` installed from a hermetic `file://` release catalog (reuse the
     existing helper). Assert before: `pkg query '%n' pfSense-pkg-pfBlockerNG-devel`
     present.
   - WHEN `pkg install` the `-NIGHTLY` `20260606` from a hermetic `nightly/<ABI>/`
     catalog. THEN it is a NAMED conflict that REPLACES `-devel`: after, `%n` ==
     `pfSense-pkg-pfBlockerNG-NIGHTLY`, `-devel` is gone, the file registry is consistent
     (`pkg check -s` / every `%Fp` present), pfBlockerNG still runs.
   - WHEN install `-devel` back over `-NIGHTLY`. THEN it replaces back (reverse
     transition). Assert both befores and afters — green must prove the replace CAUSED
     the change, not a coincidental end-state.
3. DATE-VERSION ORDERING, as a transition chain:
   - GIVEN the nightly catalog carrying only `20260605`; install → `%v == 20260605`.
   - WHEN the catalog is rebuilt to `20260606` and `pkg upgrade`. THEN `%v == 20260606`
     (before ≠ after).
   - WHEN rebuilt to `20260606.000001` and `pkg upgrade`. THEN `%v == 20260606.000001`.
     Three real transitions; assert each before and after. If any step does NOT advance,
     that is a REJECT signal — record it.
4. Land minimal `repo`-marked cases (in tests/smoke/test_repo_install.py or a sibling
   tests/smoke/test_nightly_install.py) — deselected from `-m smoke`. Use
   `unique_domain()` for any DNS; leave the VM CLEAN (`finally`/CaseContext); give long
   cases an explicit `@pytest.mark.timeout(...)`.
5. Record the VERDICT in RESULTS/01_Results.txt: GO only if the box orders the dated
   versions monotonically AND replaces across the conflict both ways; else REJECT/REDESIGN
   (cite which premise failed + the `pkg` output) per §7.
