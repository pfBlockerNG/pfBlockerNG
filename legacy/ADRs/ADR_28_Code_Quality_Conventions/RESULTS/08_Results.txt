2. ENUM ADOPTION — sites adopted vs left
-----------------------------------------

Enums (IdnMode, PfbToggle, PfbLenient) are now defined in pfb_unbound.py and
available for future phases to thread through internal call sites.

This phase deliberately stops at DEFINITION + ADAPTER level only — no internal
call site in pfb_unbound.py was changed to use IdnMode/PfbToggle/PfbLenient
instead of the plain string constants (IDN_MODE_OFF/ALL/CONFUSABLE and the
pfb["..."] comparisons).  Reason:

  §2.4 boundary rule: the pfb dict and py_unbound.ini values are STRING
  contracts with the PHP side.  Threading the enum through the main
  evaluate_domain / idn_mode_decision / idn_confusable_action paths would
  require converting at the ini-read boundary (pfb["idn_mode"] -> IdnMode)
  AND converting back at any log/write site.  That is a non-trivial wiring
  change with real regression risk in the ADR-08 Confusable/All arms, and
  the idn_mode_decision / is_idn_domain hot paths already use cheap string
  comparisons against the IDN_MODE_* constants.  The Phase-8 brief says
  "adopt narrowly" and "leave it if threading risks the boundary or the
  ADR-08 logic" — that applies here.

  The enums are now IN the right file; a future phase can adopt them at the
  read boundary (pfb_global/ini parsing) in a controlled way.  Phase 8 does
  NOT do that.


3. RE → STR SWAPS
------------------

Zero swaps made.  Same finding as the PHP Phase 7 audit:

  pfb_unbound.py's `re` uses are all genuine patterns:
  - _REGEX_* compiled constants (ReDoS detectors, feed validators) — character
    classes, quantifiers, alternation; no str method equivalent.
  - re.compile(pattern) for user rules — user-supplied patterns; cannot swap.
  - re.match / re.search with anchors + classes in the evaluate_domain path
    and ABP parser — genuine multi-feature patterns.
  - No hot-path `re` use is a single literal prefix/suffix/substring test;
    the is_idn_domain() function already uses str methods (startswith / `in`).

  No str-over-re test added (none required with no swaps).

LINE 5265 LANDMINE FIX
-----------------------
Old code: `idn_mode = cfg.get("idn_mode") or idn_mode_from_legacy(...)`
Problem: IdnMode.Off (and every IdnMode member) is truthy (backed by a non-empty
string). The `or` idiom would NEVER fall back when the key is present as Off —
evaluate_domain would always use the stored value, which is correct — but if the
stored value were Off and python_idn=True, the `or` would have bypassed Off.
Actually the bug was more subtle: IdnMode.Off is truthy, so `cfg.get("idn_mode")`
returning IdnMode.Off would NOT trigger the fallback — which is correct — but
the old `or` idiom when `pfb["idn_mode"]` was a STRING IDN_MODE_OFF ("off") was
falsy... wait, "off" is truthy. The real landmine: if cfg["idn_mode"] is None
(absent key), we want fallback; if it's IdnMode.Off, we do NOT want fallback.
The `or` is also broken for legacy callers that pass a string: an empty string
"" (which would have matched `or` to fallback) vs IDN_MODE_OFF "off" (truthy).

Fix: explicit isinstance chain:
  - isinstance(_raw, IdnMode) -> use directly (including Off; Off is NOT a fallback)
  - isinstance(_raw, str) and _raw in canonical set -> IdnMode(_raw)
  - else (None or unrecognised string) -> idn_mode_from_legacy(python_idn)

Also handles backward-compat: legacy callers (test_adr08_mode_baseline) pass
`idn_mode=IDN_MODE_ALL` (string) in cfg — the isinstance(str) branch converts it.
test_adr08_confusable_matcher passes `"idn_mode": IDN_MODE_CONFUSABLE` (string) —
same branch handles it. All existing tests pass unchanged.
