WHY THIS PHASE EXISTS
Every later phase claims "net PRODUCTION (manifest-built) decisions are unchanged" and "the query
channel is decision-equal to a real query." Those claims need a falsification harness that exists
BEFORE any code moves. This phase builds it: a golden oracle of what the production (manifest-built)
matcher decides + would log today, plus a CHARACTERIZATION of the legacy interchange-file fallback
(ADR SS1.1, re-derived 2026-07-14): the fallback runs ONLY on a manifest-build failure, it is LOSSY
(the loaders skip every NDJSON 'abp' row -- _load_ndjson_row_into_db :925 -- and regexDB/allowRegexDB
come only from the manifest build :1672, so ABP-feed rules are absent), and it is STALE-ABLE (it
reads whatever pfb_py_data.txt/pfb_py_zone.txt exist, no freshness check). Fresh plain-domain rows
DO agree with the manifest classification in both TLD-toggle states. Phase 5 removes the fallback
because it is a degraded, failure-only path -- this oracle pins the manifest decisions and records
those facts; it does NOT assert manifest==fallback equality.
