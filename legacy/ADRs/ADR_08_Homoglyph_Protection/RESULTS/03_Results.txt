2. THE EXTRACTED UNIT — SIGNATURES (Phase 4/5 import surface)
-------------------------------------------------------------
  idn_mode_from_legacy(python_idn: bool) -> str
      True  -> IDN_MODE_ALL   (today's block-all-IDN)
      False -> IDN_MODE_OFF
      The Confusable value CANNOT arise here — it only reaches Python once the PHP UI
      emits it (Phase 6). Until then this is the SOLE derivation of idn_mode.

  idn_mode_decision(q_name: str, idn_mode: str) -> bool
      Pure (stdlib only, no Unbound symbol). Returns True IFF
      `idn_mode == IDN_MODE_ALL and is_idn_domain(q_name)` — byte-equivalent to the old
      inline `cfg["python_idn"] and is_idn_domain(q_name)`. OFF and CONFUSABLE both
      return False this phase. No punycode decode, no script work.

  is_idn_domain(q_name: str) -> bool   (UNCHANGED — pure xn-- prefix match)


3. HOW idn_mode IS DERIVED (the 'on' -> All-IDN migration)
----------------------------------------------------------
  PHP ini  -> python_idn = on|off   (unchanged this phase)
  pfb_unbound init_standard: pfb["idn_mode"] = idn_mode_from_legacy(pfb["python_idn"])
    on  -> "all"   (All-IDN: every xn-- query blocked, today's exact behaviour)
    off -> "off"   (no IDN action)
  Both the matcher branch and the operate() cfg builder use a DEFENSIVE derivation
  (`cfg/pfb.get("idn_mode") or idn_mode_from_legacy(...python_idn...)`) so a cfg/pfb
  predating the key (hand-edited ini, or a unit test seeding only python_idn) still
  resolves to today's mode instead of KeyError-ing. All mode constants are truthy, so
  the `or`-fallback fires only when the key is absent/None — never masking a real "off".
