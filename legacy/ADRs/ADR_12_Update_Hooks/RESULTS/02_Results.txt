2. CONTEXT-BUILDER MAPPING (flag -> PFB_* env var)
--------------------------------------------------
The runner (Phase 1) exports PFB_WHEN always, and PFB_<KEY> per ctx entry. Phase 2 supplies:

  pre  ctx:
    TRIGGER -> PFB_TRIGGER   = pfb_hook_trigger($cron)
    (PFB_WHEN=pre added by the runner)

  post ctx:
    TRIGGER         -> PFB_TRIGGER         = pfb_hook_trigger($cron)
    IP_CHANGED      -> PFB_IP_CHANGED       = $pfb['filter_configure'] ? '1' : '0'
    DNSBL_CHANGED   -> PFB_DNSBL_CHANGED    = ($pfbupdate || $pfbpython) ? '1' : '0'
    STATUS          -> PFB_STATUS           = 'ok'   (see limitation below)
    CHANGED_ALIASES -> PFB_CHANGED_ALIASES  = ''     (see limitation below)
    (PFB_WHEN=post added by the runner)

  Source-of-truth for each (existing flags only — NO new tracking machinery):
    - $pfb['filter_configure'] (init FALSE at fn top; flipped TRUE at ~:10872 when autorules
      rule/aliastable changes are found and a filter reload is applied) = the pass-wide
      IP-side "data changed" signal. It is FINAL past filter_configure() at the post site.
    - $pfbupdate = pfb_unbound_dnsbl($mode) return (unbound.conf changed); $pfbpython =
      pfb_unbound_python($mode) return (python module/whitelist changed). BOTH are DNSBL-side
      (set in the DNSBL block ~:9393-9396), so a change in EITHER => PFB_DNSBL_CHANGED=1.
      NOTE: ADR §1 calls $pfbupdate the "IP" flag — that is imprecise; both are DNSBL. The
      accurate IP signal is $pfb['filter_configure'], used above.
      These are locals to the DNSBL block; if that block did not run they are unset, and
      !empty($unset) reads as 0 with NO PHP warning — safe at the tail.

  PFB_TRIGGER VALUES (pfb_hook_trigger($cron), verified against the callers):
    $cron 'updateip' / 'updatednsbl'  -> 'force-reload'
        (GUI Force Reload of IP-only / DNSBL-only: pfblockerng_update.php pfb_cron_update()
         -> pfblockerng.php updateip|updatednsbl -> sync_package_pfblockerng('updateip'|...))
    $cron 'cron'                       -> 'cron'
        (scheduled cron: pfblockerng.php cron -> pfblockerng_sync_cron -> ('cron');
         AND GUI Force Update + Force Reload(All): both dispatch 'pfblockerng.php update'
         which calls sync_package_pfblockerng('cron') — INDISTINGUISHABLE here)
    $cron 'noupdates'                  -> 'cron'   (cron path's "nothing to update" branch)
    $cron '' (default)                 -> 'update'
        (settings save: pfblockerng_general.php -> sync_package_pfblockerng(); also the
         de-install path -> sync_package_pfblockerng())

  => emitted set is cron|update|force-reload. The ADR's nominal 'force-update' COLLAPSES to
     'cron' because the GUI Force Update and the scheduled cron arrive with identical $cron.
     Documented in the helper's doc comment; honest label, no guessing.


3. PFB_STATUS / PFB_CHANGED_ALIASES LIMITATION (no new tracking — per ADR)
--------------------------------------------------------------------------
There is NO clean pass-wide signal for either today:
  - Errors: $parse_error is local to a per-feed download loop; .fail markers are per-feed
    files; no pass-level error/partial accumulator exists. So PFB_STATUS is hardcoded 'ok'.
  - Changed aliases: $pfb['aliasupdate'] is a per-list flag reset to FALSE each iteration
    (~:8500), not an accumulated list; no pass-wide changed-alias list exists. So
    PFB_CHANGED_ALIASES is hardcoded ''.
The ADR (§ "Load-bearing facts" / "no new tracking machinery") forbids inventing tracking,
so both ship as documented stable placeholders. A future phase MAY add real accumulation if
needed; the env-var names are already stable and present, so hooks can rely on their presence.
