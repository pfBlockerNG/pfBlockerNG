2. FIELDS + VALIDATION
----------------------
  Repeatable rowhelper table (mirrors pfblockerng_sync.php's XMLRPC-targets editor
  exactly — Form_Group->addClass('repeatable') + Add/Delete buttons; pfSense's
  rowhelper JS drives Add, Delete, AND drag-reorder natively). One row per hook:

    enabled      Form_Checkbox  -> 'on' | ''      (pfSense checkbox convention)
    when         Form_Select    -> 'pre' | 'post' (options ['pre'=>'Pre','post'=>'Post'])
    command      Form_Input(text)  the sh command line (run as root via /bin/sh -c)
    timeout      Form_Input(number) optional per-hook seconds (blank => default 60)
    description  Form_Input(text)  optional log label
    [Delete]     Form_Button (trash) per row; [Add] button below

  POST field names: <field>-<rowid> (hook_enabled-N, hook_when-N, hook_command-N,
  hook_timeout-N, hook_description-N), parsed by the same explode('-') rowhelper
  loop pattern as the sync page.

  Validation (on Save; any failure => print_input_errors, nothing written):
    - command   : reject control characters (\p{C}); reject empty/whitespace-only.
                  Shell metacharacters (; | & $ quotes) are INTENTIONALLY allowed —
                  the command is data passed to /bin/sh -c (the runner escapeshellarg's
                  it; Phase 1 proved injection-safe). NOT over-sanitised, matching how
                  pfSense shellcmd stores raw command text.
    - when      : must be a key of options_when ('pre'|'post').
    - timeout   : optional; if non-empty must pass PFB_FILTER_NUM (digits only). Blank
                  is allowed and means "use the default" (the runner's pfb_hook_timeout
                  falls back to PFB_HOOK_TIMEOUT_DEFAULT=60 for blank/invalid/<=0).
    - description: reject control characters.

4. CONFIG ROUND-TRIP — EXACT PHASE-1 SCHEMA (verified)
------------------------------------------------------
  The page reads/writes the SAME path + keys the Phase-1 runner consumes:
      Path : installedpackages/pfblockerng/config/0/hooks      (a numeric list)
      Keys : { command, when, enabled, description, timeout }  per entry

  Save rebuilds the list from POST IN ROW ORDER (config_set_path on the whole list;
  config_del_path when the list is emptied — i.e. all rows deleted), so list order ==
  hook run order, matching pfb_get_hooks (which preserves list order).

  Verified end-to-end with a standalone PHP simulation: a 2-row submit (an enabled
  post hook + a disabled pre hook) through the page's save logic produced
      hooks[0] = {command,when:'post',enabled:'on',description,timeout:'30'}
      hooks[1] = {command,when:'pre',enabled:'',...}
  and the VERBATIM Phase-1 pfb_get_hooks($cfg,'post') returned 1 entry,
  pfb_get_hooks($cfg,'pre') returned 0 (the disabled row correctly skipped). Schema
  match confirmed by feeding the read helper, not by eyeballing keys.


5. HELP TEXT (truthful per Phase-2 RESULTS/02)
----------------------------------------------
  Four StaticText help blocks in the first section:
    - About      : once-per-pass semantics; disambiguation from ip_pre_*.sh.
    - Run as root: runs AS ROOT via /bin/sh -c (same trust as shellcmd/cron);
                   admin-only; /usr/bin/timeout kills a hung hook (SIGTERM, then
                   SIGKILL after a grace period); non-zero exit OR timeout is logged
                   and the update CONTINUES (a hook can never abort/stall an update);
                   Pre hooks run before processing, Post hooks after everything, in
                   list order.
    - Environment: documents EXACTLY what Phase 2 emits —
                   PFB_WHEN (pre|post; both fire points),
                   PFB_TRIGGER (cron | update | force-reload; both fire points) with
                     the honest note that GUI Force Update / Force Reload(All) arrive
                     as 'cron' (the ADR's nominal 'force-update' collapses to 'cron'),
                     'update' = a settings save, 'force-reload' = a GUI IP-only/DNSBL-only
                     Force Reload,
                   and the POST-ONLY vars (a pre hook runs before anything is downloaded):
                     PFB_IP_CHANGED (0|1), PFB_DNSBL_CHANGED (0|1),
                     PFB_STATUS (currently always 'ok' — reserved/placeholder),
                     PFB_CHANGED_ALIASES (currently always empty — reserved/placeholder).
                   No value the code does not emit is promised.
    - HA / sync  : hooks live in config => replicate to a CARP/HA secondary and run on
                   whichever node performs the update.
  A page-foot callout notes hooks run on the next CRON update or Force Update|Reload.
