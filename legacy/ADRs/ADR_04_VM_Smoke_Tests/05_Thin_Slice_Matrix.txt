WHY THIS PHASE EXISTS
"Test all combinations of DNSBL settings" is the long-term goal, but landing it all at
once is a huge, slow-to-green PR. A thin slice proves the loop (config -> reload ->
probe -> assert) works on real pfSense for the representative shapes, then the matrix
grows in follow-up changes. This is the deliverable that turns ADR-03/01's "manual
smoke, owner: maintainer" into an automated regression guard for the covered cases.

ACTION PLAN (ordered)
1. IP CASE: register a mock feed serving a known set of IPs into an alias; reload
   (updateip); assert `pfctl -T show <alias>` contains every fed IP and EXCLUDES a
   non-fed IP; assert a rule references the alias (`pfctl -sr`). One positive + one
   negative member.
2. DNSBL CASES (parametrised over the loop): for a domain served by the mock DNSBL
   feed —
   a. EXACT block, response mode NXDOMAIN -> `dig A` rcode NXDOMAIN; exact match does
      NOT block a subdomain (data=exact: `x.<domain>` is NOT blocked).
   b. EXACT block, response mode NULL-IP -> `dig A` returns the configured null addr
      (and AAAA per the configured behaviour).
   c. WILDCARD (zone) block -> blocks `<domain>` AND a deep subdomain
      `a.b.<domain>` (incl self), per the zone=wildcard contract.
   d. WHITELIST passthrough -> a domain on the whitelist (and also present in the
      block feed) RESOLVES to its local-data answer, not the block shape.
3. HERMETIC CHECK: ensure every expected answer comes from mock feeds + baked
   local-data; add/keep a job mode (or note for Phase 6) that runs with runner egress
   blocked and still passes (ADR §4 req 4).
4. FALSE-GREEN GUARD: include one case whose expectation is deliberately wrong, marked
   xfail(strict) (or an explicit assert-it-fails), so a harness that silently passes
   everything is caught.
5. Keep ALL of these under `@pytest.mark.smoke`; the default run must stay clean.
