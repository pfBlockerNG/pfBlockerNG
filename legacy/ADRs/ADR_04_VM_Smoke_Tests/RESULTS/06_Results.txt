TRIGGER — chosen + why
-------------------------------------------------------------------
GATED: workflow_dispatch + workflow_call only (a nightly `schedule` is present
but COMMENTED). NOT every-PR.
WHY: the per-run wall-time is UNMEASURED (RESULTS/05 left `pytest -m smoke`
wall-time PENDING the first CI run; this environment has no /dev/kvm/image/
secrets to measure it). ADR §7's budget is <= ~20 min/job. Shipping flaky/slow
every-PR CI before measuring is exactly what §7 forbids. MOVE TO EVERY-PR by
adding a `pull_request` trigger once a dispatched run confirms it fits the budget.
FORWARD-COMPAT (ADR-09): the image ref is an INPUT (image_ref), defaulting to the
single supported CE version's GHCR ref/secret. No version fan-out/matrix/schedule
logic here — that is ADR-09. workflow_call-able so ADR-09 can drive it per version.

CANDIDATE pfBlockerNG BEHAVIOURS SURFACED (NOT bugs to fix here)
-------------------------------------------------------------------
From RESULTS/05 (semantic gotcha, intended behaviour, pinned by
test_dnsbl_exact_nxdomain): in DNSBL *python* mode WITHOUT the TLD feature, every
feed domain is an EXACT (dataDB) entry — there is NO wildcard/subdomain blocking.
Operators expecting a plain blocklist domain to also block its subdomains in
python mode would be surprised; wildcard blocking needs Unbound mode (redirect
zone) or the TLD feature. If a future ADR wants python-mode wildcards that is a
src/ change for its own PR — OUT OF SCOPE here. No new behaviours surfaced this
phase (no live run performed here).
