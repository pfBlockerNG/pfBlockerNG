WHY THIS PHASE EXISTS — THE DEVEL-VS-NEXT GAP (read RESULTS/07_Results.txt FIRST)
On the live CE VM (devel), verified empirically (NOT inferred):
  * A DNSBL block is `NOERROR` + an A record of the sinkhole IP — NEVER NXDOMAIN
    (the only NXDOMAIN path in pfb_unbound.py is SafeSearch). null (0.0.0.0/::0)
    vs the VIP is the `null_blocking` flag: a normal feed match sets log_type "1"
    -> null_blocking=False -> the block answers the DNSBL VIP (`dnsbl_ipv4`).
  * UNBOUND mode writes EXACT `local-data: "<d> 60 IN A <vip>"` (NOT a
    `local-zone redirect` wildcard, contrary to the ADR's original reading) — it
    sinkholes the exact listed domain to the VIP and leaves subdomains untouched.
  * PYTHON mode (dnsbl_python + pfb_py_block) did NOT engage for the firewall's
    OWN (localhost / 127.0.0.1) query, while UNBOUND mode DID. The single-NIC
    smoke VM has only localhost + WAN (no LAN client), and the WAN-sourced query
    (runner hostfwd) is not served, so python-mode blocking could not be exercised
    on devel. This was NOT a misconfig: module loaded (`module-config: "python
    iterator"` + `python-script: pfb_unbound.py`), `python_blocking=on` in
    /var/unbound/pfb_unbound.ini, the domain present in /var/unbound/pfb_py_data.txt
    (log_type 1), py_error.log empty. It is a source/topology limitation of how
    python-mode treats on-box queries.

So on `next` (python-mode-only, Unbound mode gone) the matrix MUST be reworked.
