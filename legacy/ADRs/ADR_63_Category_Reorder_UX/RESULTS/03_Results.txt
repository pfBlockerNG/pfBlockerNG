== CARRY-FORWARD FOR PHASE 4 ==
- roworderdragging read/emit pattern (mirror exactly):
    PHP: `config_path_enabled('system/webgui', 'roworderdragging')` (no
    third-arg default needed -- pfSense's own 'enable' default doesn't apply
    here since we pass the key explicitly).
    JS emission: `var pfb_drag_enabled = <?=config_path_enabled('system/webgui', 'roworderdragging') ? 'false' : 'true';?>;`
    placed as a page-level var (alongside category.php's existing
    `var pagetype = null;`), NOT inside events.push -- it must be readable by
    the pfb_reorder_init() call site, which itself CAN live inside
    events.push (fine either way, since the var itself is set synchronously
    at parse time, before events.push's queued callback runs).
- pfb_reorder_init call shape used here:
    `pfb_reorder_init('#pfb_table table tbody', 'tr.sortable', null, pfb_drag_enabled);`
    container = the SAME selector the old `.sortable()` init and the old
    `.sortable('serialize')` read both used (category.php's tbody, NOT the
    outer panel div) -- for category_edit.php (Phase 4) the equivalent
    container is `'#pfb_repeat'` (per Phase-2's own fixture, matching
    `$group->addClass('repeatable')`'s parent), rowSelector
    `'.form-group.repeatable'` (Phase-1's F-facts, ADR-63 carry-forward),
    onAfterMove is NOT null there -- category_edit.php has no server-side
    ids[] AJAX Save today (Phase 1: reordering there is exclusively the
    Lmove/Xmove POST mechanism or the sort=='sort' auto-sort pass); Phase 4
    must supply a real onAfterMove that composes with pfSenseHelpers.js's
    renumber() the same way Phase-2's fixture (pfbFixtureOnAfterMove) does,
    per Phase-2's CARRY-FORWARD items 2-4 (bump_input_id() quirks, the
    gutter-refresh-after-delete binding trap).
- onAfterMove=null is safe/intentional on category.php specifically because
  the component's own zero-checked-anchor-click firing (Phase-2 DEVIATION 1)
  can never reach anything -- there is no dirty-state/gutter/renumber
  side-effect to avoid triggering. Phase 4, which likely needs a REAL
  onAfterMove (renumber+gutter), must re-examine whether the zero-checked
  firing there is still safe or needs its own guard.
- The reorder `<th>` gating pattern (`if ($gtype != 'geoip')`, mirroring the
  existing Frequency-column gate) is category.php-specific (GeoIP has no
  analogous "second table shape" concern on category_edit.php, which has no
  GeoIP edit view at all -- Phase-1's F6: the page's gtype switch is
  {ipv4, ipv6, dnsbl} only, no geoip case).
