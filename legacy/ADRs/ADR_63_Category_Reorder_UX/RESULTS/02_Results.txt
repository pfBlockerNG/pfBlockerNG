HYPOTHESIS LEDGER (debugging protocol): the fixture's original
`$('#pfb_repeat').on('click', '[id^=deleterow]', refreshGutter)` (a
container-DELEGATED handler) never ran its refresh after core's
`delete_row()` removed the row. H1 (CONFIRMED by fix + green re-run):
core's delete_row() is bound DIRECTLY on the button (fires in the button's
own target-phase dispatch, separate from #pfb_repeat's delegated dispatch
which runs later as the event continues to bubble); it removes the row+button
from the DOM synchronously. By the time the SEPARATE delegated dispatch on
#pfb_repeat runs, the row is already detached, and jQuery's target-match walk
for that later dispatch never re-attaches the (now-orphaned) event.target to
the container, so the delegated handler is skipped. H2 (refreshGutter() itself
buggy) was ruled out: the observed values (stale pre-delete gutters minus the
removed one, NOT renumbered) are exactly what "handler never ran" predicts,
not what a buggy renumbering function would produce.

gutter-refresh DIRECTLY on each delete button (not delegated on the
container), rebinding after every add_row() the same way core itself
rebinds its own delete handlers after every clone (`.clone()` copies no
handlers) -- so ours runs in the SAME per-button dispatch pass, strictly
after core's, immune to the detached-target issue. See CARRY-FORWARD.

== COMPONENT PUBLIC SURFACE (for Phase 3/4) ==
pfb_reorder_init(container, rowSelector, onAfterMove, dragEnabled)
  - container: jQuery selector STRING or element -- the delegation root AND
    (if dragEnabled) the .sortable() target.
  - rowSelector: 'tr.sortable' (category.php) or '.form-group.repeatable'
    (category_edit.php).
  - onAfterMove: function(), called after EVERY completed drag-stop or
    anchor-click move (including a zero-checked anchor-click -- see
    DEVIATIONS). Page-side glue (renumber(), a gutter refresh, etc.) belongs
    HERE, not in the component (kept minimal per the brief).
  - dragEnabled: boolean. true -> .sortable() initialised with category.php's
    existing options (items:rowSelector, cursor:'move', distance:10,
    opacity:0.8, the same width-fixing helper) plus a stop callback firing
    onAfterMove. false -> .sortable() is NEVER called on the container.
  - Injects, per row (idempotent -- skips a row that already has one): a
    checkbox (`.pfb-reorder-chk`, id `pfb_reorder_chk-{i}`) and a
    type="button" anchor (`.pfb-reorder-anchor`, id `pfb_reorder_anchor-{i}`).
    Click = move all OTHER checked rows immediately BEFORE the clicked row;
    shift-click = AFTER. Event handling is delegated on `container`
    (namespaced `click.pfb_reorder`, safe to call init() more than once).

pfb_reorder_read_order(container, rowSelector) -> string
  Returns the current DOM order of row ids in `ids[]=rN&ids[]=rM&...`
  format, computed directly from the DOM (byte-identical to
  `$(container).sortable('serialize',{key:'ids[]'})` but works even when
  .sortable() was NEVER initialised -- the ADR sec1.8 trap). Per-row token =
  the substring after the id's LAST `-`/`=`/`_` (regex `/(.+)[-=_](.+)/`,
  matching jQuery UI's own serialize regex), URL-encoded; a row id with no
  such separator contributes no token; an empty container returns ''.

== DEVIATIONS / JUDGMENT CALLS ==
1. Zero-checked anchor-click still fires onAfterMove (brief sec4 explicitly
   left this as "define whether onAfterMove still fires and assert it").
   Chosen: fires unconditionally -- "a completed anchor-click" is the
   contract event, not "a completed move"; simpler mental model, no special
   case in the component. Tested and asserted explicitly.
2. The insert-order algorithm for multi-row straddle (brief left the exact
   mechanism unspecified, only "a well-defined final order"; firewall_rules.php
   was explicitly NOT required reading this phase): checked rows are walked
   top-to-bottom and inserted immediately before the anchor (plain click), or
   walked bottom-to-top and inserted immediately after it (shift-click) --
   preserves the checked rows' original relative order, contiguous with the
   anchor. Documented in a 3-line code comment; the 3 straddle test cases
   pin the exact resulting order.
3. A fixture-only bug (NOT the shared component): the test fixture's
   original gutter-refresh-after-delete hook was container-DELEGATED and
   missed core delete_row()'s already-removed target (see HYPOTHESIS LEDGER
   above). Fixed by binding directly on each delete button, matching core's
   own rebind-after-clone convention. This is test/fixture glue in
   tests/smoke/ui/test_reorder_component.py, not a change to pfBlockerNG.js.
4. No red-before-green TDD proof for the component itself: this is brand-new
   code (CLAUDE.md's "brand-new code with no pre-existing behaviour to be
   wrong" carve-out) -- the mandated substitute is the failability mutation

== CARRY-FORWARD FOR PHASE 3/4 ==
- Component surface: see COMPONENT PUBLIC SURFACE above -- call
  pfb_reorder_init(container, rowSelector, onAfterMove, dragEnabled) once per
  page; dragEnabled should be `!roworderdragging` (ADR sec2 Decision 2, read
  server-side via config_path_enabled('system/webgui/roworderdragging')).
- pfSenseHelpers.js quirks observed on the REAL VM (load-bearing for Phase 4's
  category_edit.php wiring):
  1. renumber()/add_row()/delete_row()/checkLastRow() operate on GLOBAL
     `$('.repeatable')` -- category_edit.php already only ever has ONE such
     cluster per page load (matches this fixture's design), so this is a
     non-issue there, but never add a SECOND `.repeatable` group to that page.
  2. add_row()'s bump_input_id() only rewrites <input>/<select>/
     [id^=deleterow] -- NOT a generic <button>. The component's own injected
     anchor button can therefore carry a stale/duplicate id for one add_row()
     cycle if no move (hence no renumber()) has run since the last
     structural change. Inert for the component's OWN logic (row identity is
     always resolved via DOM traversal, never by parsing the anchor's own
     id -- see the component's file-header comment), but Phase 3/4's page
     wiring should call renumber() again after its own add-row handler
     (exactly what this phase's fixture now does) to keep the DOM's ids
     fully clean, not just functionally inert.
  3. A gutter/visual-refresh hook bound on core's delete_row() must NOT be a
     container-delegated handler -- core's own delete handler (bound
     directly on the button) removes the row before the event finishes
     bubbling to a delegated ancestor listener, so the delegated handler can
     be skipped entirely (see HYPOTHESIS LEDGER). Bind directly on each
     delete button instead, REBINDING after every add_row() (mirroring how
     core itself rebinds its own delete handlers after every `.clone()`,
     since clone() copies no handlers). This phase's fixture
     (pfbFixtureBindDeleteRefresh()) is the reference pattern.
  4. add_row()'s clone via bump_input_id() clears <input> values (`url-`/
     `header-`) but LEAVES <select> selections (`format-`/`state-`)
     unchanged -- a newly-added row inherits the PREVIOUS last row's
     format/state selection, not a blank default. category_edit.php's own
     production defaults may differ; verify this if Phase 3/4 asserts a
     specific new-row default.
- GeoIP order-persist no-op (issue #1201, Phase 1) remains untouched and
  out of scope -- this phase adds no GeoIP-specific behaviour.
- The 3 fixture pages + their generator functions in
  tests/smoke/ui/test_reorder_component.py are test-only artifacts (never
  shipped) -- Phase 3/4 does not need to reuse them, only the component
  they exercise.
