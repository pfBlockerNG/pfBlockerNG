CONTEXT / PROBLEM
Stage 1 (phase 02) unified only the DNSBL axis. Three query-time memos remained for
the other subsystems: excludeAAAADB (noAAAA negative, list), excludeSS (SafeSearch
negative, list), and noAAAADB[name] = True (the noAAAA wildcard->exact query-time
memo). These are exactly the "should've been sets" warts.

DECISION
Make the Decision the single per-domain verdict across ALL axes. decisionDB values
become a COMPOSED Decision with three lazily-filled axes (dnsbl / noaaaa /
safesearch); an UNSET sentinel distinguishes "axis not yet evaluated" from an
evaluated allow/no-match. Each axis decides at its own point in operate() (noAAAA +
SafeSearch pre-resolution on q_name_original, DNSBL post-resolution on the chain), so
the entry is created on first touch (_decision_for) and filled per axis. The lists +
the memo dissolve -- their negative-memo role becomes a cached noaaaa = False /
safesearch = None, so the set-vs-list question disappears by REMOVAL.

FINDINGS
- find_noaaaa_wildcard_parent uses a TRUTHY check, so the SOURCE noAAAADB value
  (wildcard flag) is load-bearing -- it stays a dict[str,bool], NOT a set. Only the
  query-time memo was set-like, and it's gone.
- get_details_reply's two noAAAA-label reads were coupled to the removed memo ->
  switched to evaluate_noaaaa (exact + wildcard), so wildcard-child replies are now
  labelled correctly. Pinned by test_reply_x_aaaa_wildcard_child_proceeds (proven to
  fail without the switch).
- The SafeSearch cname branch's pre-existing "wait for Unbound code changes" TODO was
  researched: no native pythonmod CNAME-chasing exists in Unbound 1.22.0 (pfSense
  2.8.0) through 1.25.x. The underlying defect is tracked open as NLnetLabs/unbound#976
  ("CNAME in local-data: is not resolved") -- now referenced in the TODO.
