WHY THIS PHASE EXISTS
Today pfBlockerNG sends NO conditional request: the detector does a HEAD to read Last-Modified and
compares client-side, and the remote md5 fallback re-downloads the WHOLE feed. A real conditional
GET (If-None-Match from a stored ETag; If-Modified-Since from a stored Last-Modified) lets the server
answer 304 (empty body) -> skip the download entirely. pfb_download already has a dead 304 handler
(inc:7694) waiting to be armed.

ACTION PLAN
1. Persist per-feed validators on each successful 200: store the response `ETag` and `Last-Modified`
   as sidecar files next to `.orig` (tagged, e.g. `{base}.etag` / reuse the Last-Modified the code
   already reads). Use the Phase-1 sidecar-write style.
2. On the next fetch, send `If-None-Match: <stored ETag>` (primary) and, when no ETag is stored,
   `If-Modified-Since: <stored Last-Modified>` (CURLOPT_TIMECONDITION). Arm the 304 handler:
   304 -> treat as UNCHANGED (no re-download, no re-ingest), keep the cached `.orig`.
3. On 200: download as today, then DECIDE re-ingest by hashing the fetched bytes (xxh128) vs the
   persisted source hash (Phase-1/2 helper) — a spurious 200 with identical bytes does NOT re-ingest
   (contract #5). Update the stored validators + hash.
4. Remove the detector's HEAD-then-client-compare for remote feeds (the conditional GET subsumes it);
   keep download-then-hash ONLY as the last resort when the server offers neither validator.
5. Smoke (mock-feed server): (a) unchanged feed + matching validator -> 304 -> not re-downloaded/
   re-ingested; (b) changed feed -> 200 -> hashed -> re-ingested; (c) server with NO validator ->
   download + hash decides; (d) spurious 200 identical bytes -> no re-ingest. Assert via the response
   path + the detector log + a DNS/probe outcome where applicable.
