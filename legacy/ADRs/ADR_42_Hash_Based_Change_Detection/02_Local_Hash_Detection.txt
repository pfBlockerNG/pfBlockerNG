WHY THIS PHASE EXISTS
mtime is whole-second on pfSense, so a content change within the same second as the last ingest is
MISSED today (the blind spot #540 left open). This phase makes the local-feed gate content-addressed
via xxh128, using the tagged read/write helper from Phase 1, closing that hole.

ACTION PLAN (tests express intent; red->green for the new behaviour)
1. In the local-file branch of `pfb_update_check`, REPLACE the mtime compare (+ #540 md5-confirm)
   with: read the persisted source hash (tagged helper), compute `xxh128(source)`, and treat the
   feed as changed iff they differ (or the persisted value is absent/unknown -> changed). On a
   detected change (and after the sync re-ingests) the persisted hash is rewritten via the Phase-1
   write helper (`.xxhash128`, deleting any legacy `.md5`). mtime is no longer the gate.
2. Keep the existing `.update` marker contract (touch on change) so the downstream sync path is
   unchanged — this phase changes only HOW "changed" is decided.
3. PHPUnit: pin the new decision — content-identical -> unchanged; content-different -> changed;
   legacy `.md5` present -> reads md5, then a change writes `.xxhash128` + removes `.md5`; absent ->
   changed; idempotence (same content twice -> no re-ingest).
4. Smoke: migrate the three #538/#540 cron cases from mtime to hash semantics, and ADD a
   same-second case — write a local feed, ingest, then rewrite DIFFERENT content while forcing the
   source mtime EQUAL to the prior (`touch -r` the old mtime onto it) so mtime cannot distinguish;
   a `cron` run MUST now detect+re-ingest (RED on pre-change mtime code, GREEN after). Drive via the
   genuine `cron` verb (not force_dnsbl_refetch).
