WHY THIS PHASE EXISTS
The scheduled-reset feature pivots on one decision: "has the calendar period rolled
over since the last reset?" Isolating that as PURE functions (no I/O) lets us pin
every branch off-box before any risky log truncation or cron wiring exists. The cron
cadence is operator-defined, so the logic MUST be boundary-gated (period-changed),
not tick-counting (ADR §1.2).

ACTION PLAN (tests FIRST)
1. Write tests/php/LogRotateScheduleTest.php that pins the intended behaviour:
   - pfb_log_rotate_period($schedule, $ts) returns:
       'off'/'' -> ''   ; 'daily' -> 'YYYY-MM-DD' ; 'weekly' -> ISO 'YYYY-Www'
       (use date('o-\WW', $ts) so the ISO week-year is correct) ; 'monthly' -> 'YYYY-MM'.
     Assert concrete values for fixed timestamps, INCLUDING the ISO-week year-boundary
     case (e.g. 2027-01-01 falls in ISO week 2026-W53 — assert it).
   - pfb_log_should_reset($schedule, $last_key, $now_ts):
       off/'' -> FALSE (every time) ;
       schedule set AND period(now) === $last_key -> FALSE (same period, no reset) ;
       schedule set AND period(now) !== $last_key -> TRUE ;
       schedule set AND $last_key === '' (never reset) -> TRUE.
     Branch coverage: assert BOTH sides of each boundary (before-and-after), not one.
2. Implement the two functions in pfblockerng_extra.inc (pure; type-hinted; no I/O,
   no globals, no config reads). Default an unrecognised $schedule to off-behaviour.
